RunWisp has one password and one session. Type the password, get a
session, and use that to drive the Web UI, TUI, and REST API. No
users, no roles, no API keys. The trust model is "if you can log in,
you control the daemon", and RunWisp is built for one operator on one
machine.

## Logging in

The Web UI shows a single password field. The TUI opens the browser
straight in when you start it locally with `runwisp`, or asks for the
password via env var / CLI flag when you connect to a remote daemon.

Your password never travels over the network as plain text. The login
uses **SRP** (RFC 5054 / RFC 2945), a password-authenticated key
agreement protocol: the browser and daemon exchange ephemeral keys and
zero-knowledge proofs, and at the end of the exchange they have each
verified the other knows the password — without either side disclosing
it. Even on plain HTTP behind a TLS-terminating proxy, a passive
eavesdropper sees no material brute-forceable against the password.

The daemon **does not store your password.** Only a verifier — a
one-way function of the password and a per-installation salt —
lives on disk. Forgetting the password means resetting it (see
"Rotating the password" below), not recovering it.

After a successful login the daemon issues a session in a secure
cookie. Restart the daemon to invalidate every session at once.

## The password

The data directory is created with `0700` perms and `runwisp.db` is
`0600` — only the daemon's user can read it. **What lives in SQLite is
the SRP verifier and salt, not the password itself.** On first run
RunWisp generates a random password, computes a verifier, stores the
verifier+salt, and prints the password once to stdout.

> **Save the password the first time you boot.** It is shown exactly
> once. RunWisp cannot recover it later — the daemon never had it.

`RUNWISP_PASSWORD` overrides the on-disk verifier with one derived
in memory. The env-supplied verifier is **not** persisted, matching
the contract you expect from Docker secrets, systemd's
`LoadCredential=`, or sealed-secrets workflows.

### Rotating the password

To set a new password you can either:

- Export `RUNWISP_PASSWORD` to the new value and restart the daemon.
  The env-supplied verifier overrides the stored one in memory only.
- Delete the `srp_verifier` and `srp_salt` rows from `config_entries`
  and restart. The daemon will generate a fresh random password on
  next boot.

Either path invalidates every existing session, because changing
`RUNWISP_PASSWORD` rotates the JWT signing secret.

### Trust boundary

The daemon's filesystem is the trust boundary. Anyone who can read
the data directory can:

- Read the JWT signing secret and mint admin tokens (the CLI does
  exactly this to authenticate locally without prompting for the
  password).
- Read the SRP verifier, which is brute-forceable in principle but is
  also PBKDF2-stretched with 600 000 iterations.

That is why the data directory ships with `0700` perms, the DB with
`0600`, and why `RUNWISP_DATA_KEY` exists for operators who need at-
rest encryption on top.

## Rate limiting

Failed login attempts are rate-limited per source IP. Cross the limit
and you get `429 Too Many Requests` until the window slides past;
restarting the daemon clears the counter.

Live log streams are limited too — at most a few dozen open at once,
plus a small per-IP cap — so a buggy script can't accidentally exhaust
the daemon. If you hit the limit, the response is `503 Service
Unavailable`; close some open log views and try again.

## Reverse proxies

RunWisp binds to `127.0.0.1:9477` by default and serves plain HTTP.
To expose it publicly with TLS, run a reverse proxy in front (nginx,
Caddy, Traefik, Cloudflare Tunnel, …) and tell the daemon which IP
ranges that proxy lives on:

```bash
export RUNWISP_TRUST_PROXY='10.0.0.0/8,2001:db8::/32'
runwisp daemon --host 127.0.0.1 --port 9477
```

`RUNWISP_TRUST_PROXY` is a comma-separated list of CIDR ranges whose
`X-Forwarded-Proto` and `X-Forwarded-For` headers RunWisp will trust.
When a request from a trusted range arrives with `X-Forwarded-Proto:
https`, the daemon treats the connection as secure and marks the
session cookie accordingly. Rate limiting always counts the real TCP
peer, not the forwarded header, so a misconfigured proxy can't open a
hole.

The daemon rejects `0.0.0.0/0` and `::/0` — trusting the entire
internet would let any client lie about its source IP.

## Encrypting secrets at rest (`RUNWISP_DATA_KEY`)

By default the daemon protects its SQLite secrets with filesystem perms
alone — the data directory is `0700` and the `runwisp.db` file is
`0600`. That's enough for the typical single-tenant box. If you want
defense against a stolen drive image, leaked backup, or co-tenant root,
encrypt the secret rows at rest.

Generate a key:

```bash
export RUNWISP_DATA_KEY=$(runwisp keygen)
```

`runwisp keygen` prints a base64-encoded 32-byte key. Save it somewhere
your secrets manager owns — **not** in the data directory it protects.
Once the daemon boots with `RUNWISP_DATA_KEY` set, every secret row in
SQLite (password, JWT signing secret, env-password fingerprint) is
re-written with AES-256-GCM ciphertext under the `enc:v1:` prefix.

The daemon refuses to start when the data dir is encrypted and
`RUNWISP_DATA_KEY` is missing or wrong. **Losing the key bricks the
data directory** — there is no recovery short of wiping the secrets
and re-deriving them.

To stop encrypting at rest, you must first manually decrypt the rows
(or wipe them) before unsetting `RUNWISP_DATA_KEY`. The daemon will
not silently downgrade.

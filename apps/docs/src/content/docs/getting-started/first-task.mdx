This page takes you from "binary on disk" to "task running and streaming
logs" in about five minutes. We will define one scheduled task, one
long-running service, start the daemon, and explore the result in the TUI.

## 1. Scaffold a `runwisp.toml`

From your working directory:

```bash
runwisp init
```

This drops a `runwisp.toml` next to you with one task, one service, and
inline comments next to every key. It is the fastest way to see the full
schema without flipping between docs and an editor. The scaffold also
writes `[scheduler] timezone = "<your-system-zone>"` so your cron
expressions are evaluated in the timezone you actually live in (you can
edit that to any IANA zone — `Europe/Bratislava`, `America/New_York`,
`UTC` — or remove it to fall back to the host's system zone).

![first-task-init.png — Terminal showing `runwisp init` output: a path to the new runwisp.toml, the detected system timezone, and a generated password.](../../../assets/screenshots/placeholder.svg)

Open it up — the relevant pieces look roughly like this:

```toml
# runwisp.toml

[tasks.backup-db]
cron       = "0 2 * * *"  # every night at 2 AM
on_overlap = "skip"       # do not stack if the previous run is still going
keep_runs  = 30
run = "pg_dump mydb | gzip > /backups/mydb-$(date +%F).sql.gz"

[tasks.health-check]
cron = "*/5 * * * *"      # every five minutes
run  = "curl -sf https://myapp.example.com/health || exit 1"

[services.worker]
instances = 3             # keep three replicas always running
run       = "node /app/worker.js"
```

**`[tasks.*]`** are units that run on a schedule (or on demand). Each task
gets its own concurrency policy, retry settings, log retention, and timeout.

**`[services.*]`** are always-on processes. RunWisp keeps them alive with
exponential restart backoff, surfaces their stdout/stderr like any other
run, and supports horizontal scaling with `instances = N`.

:::note[One namespace for both]
Task and service names share a single namespace — `[tasks.worker]` and
`[services.worker]` is rejected at startup. Pick a unique name per
unit; the daemon refuses to boot if two collide.
:::

Edit the scaffolded file to match the work you actually want to run, or
paste the example above over it to follow along with this guide.

## 2. Start RunWisp

```bash
runwisp
```

`runwisp` (with no subcommand) spawns the daemon in the background and
attaches the interactive **TUI**. The TUI's Home page shows the Web UI
URL and — on first run only — an auto-generated **login password** that
the daemon wrote to disk for you. Press `Enter` on the password row to
copy it to your clipboard; you will need it for the Web UI.

![first-task-tui-home.png — TUI Home page on first start: ▸ ⮕ Open Web UI focused at top, Web UI URL row with localhost:9477, and an auto-generated password row.](../../../assets/screenshots/placeholder.svg)

Want it to run in the background, with no terminal UI (for `systemd`
or a Docker `CMD`)? Use `runwisp daemon` instead.

## 3. Watch it run

Inside the TUI you can:

- Browse all configured tasks and services in the sidebar.
- Open a task to see its run history and stream live logs.
- Press <kbd>r</kbd> to trigger a task manually without waiting for the
  schedule.
- Cancel a run that's still going, requeue it, or jump to the failure
  that woke you up at 3 AM.

![first-task-tui-run.png — TUI exec view mid-run for the `health-check` task: header with run ID and elapsed time, line-numbered log streaming live with each curl response.](../../../assets/screenshots/placeholder.svg)

To trigger from the command line instead, leave the TUI running and open
another shell:

```bash
runwisp exec health-check
```

The output streams back to your terminal, and the run is recorded in the
daemon's history exactly as if it had fired on schedule.

## 4. Open the Web UI

The TUI's Home page lists `▸ ⮕ Open Web UI` as its first focusable row
— press `Enter` and your browser opens straight into the dashboard,
already logged in. Or just point a browser at `http://localhost:9477`
and paste the password from step 2. You will see the same task list,
run history, and live log streaming from a browser. Set the
`RUNWISP_PASSWORD` environment variable to pin a password of your own,
or pass `--host` / `--port` to change the bind address.

![first-task-web-ui.png — Web UI dashboard after login: sidebar with `backup-db` and `health-check` under Tasks plus `worker` under Services, recent activity feed showing a successful `health-check` run.](../../../assets/screenshots/placeholder.svg)

## What just happened

- RunWisp parsed your TOML, set up scheduling for `backup-db` and
  `health-check`, and started three replicas of `worker`.
- Every run, scheduled or manual, gets a ULID, a row in embedded SQLite,
  and a per-task log file on disk.
- If the daemon is force-killed right now (or the server crashes) and
  you restart it, the `worker` runs that were still going will be marked
  **crashed** with exit code `-2` — your history stays intact and the
  next firing is a fresh execution.

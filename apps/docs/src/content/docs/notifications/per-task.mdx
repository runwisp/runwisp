When it's just one task you care about, skip the routing rules and name
the channels right on the task. The setting sits next to the task it
belongs to, so a glance at the file tells you which task pages which
channel.

Every `[tasks.*]` and `[services.*]` block takes a [`notify`](/configuration/tasks/#notify) field: the
channels to page whenever the run counts as a **failure** (by default
`failed`, [`timeout`](/configuration/tasks/#timeout), `crashed`, `log_overflow`, `start_failed`, and a
missed tick — whatever the task's
[`failures`](/configuration/tasks/#failures) list says).
It works the same on tasks and services. Want to hear about a _success_,
or some other specific outcome? That's a one-line
[`[[route]]`](/notifications/routes/) — see
[Beyond failures](#beyond-failures) below.

## Basic usage

```toml
[tasks.nightly-db-backup]
cron              = "30 2 * * *"
run               = "/usr/local/bin/backup.sh"
notify = ["slack-ops"]
```

That's the whole setup. A failed backup lights up the `slack-ops`
channel, drops a row in the bell, and lands in the notification history.
The bell part is free: `"inapp"` sits in `[notify] global_notifiers` by
default, so it tags along on top of whatever channels you name. Don't
want it? Set `global_notifiers = []` to silence it (see
[Global settings](/notifications/global/#the-bell--global_notifiers)).
And if a notification rule happens to match the same event too, each
channel still gets exactly one message — duplicates are dropped.

## Beyond failures

[`notify`](/configuration/tasks/#notify) covers the failure case, which is the one you almost always
want. For anything else — a success ping, an alert scoped to just
timeouts — reach for a [`[[route]]`](/notifications/routes/), which
matches on event kind and a task glob:

```toml
[services.payments-api]
instances         = 2
run               = "/usr/local/bin/payments-api"
notify = ["slack-ops", "tg-oncall"]   # any failure → two channels

# A clean shutdown pings one channel.
[[route]]
match     = { task = "payments-api", kinds = ["succeeded"] }
notifiers = ["slack-ops"]
```

The per-task [`notify`](/configuration/tasks/#notify) and the rule are independent and mix freely — the
router collects every channel that matches and sends one message per
unique channel.

## Missed-run alerts

There's no separate missed-run channel list, and that's deliberate. A
[missed scheduled run](/concepts/scheduling/#alerting-on-missed-runs) —
one the daemon was down for — counts as a failure by default, so it rides
the **exact same channels you already named in [`notify`](/configuration/tasks/#notify)** (plus
the bell, via `global_notifiers`). You don't wire it up; it's just there.

What you _can_ do is stop treating misses as failures for a task that's
expected to miss ticks — a laptop job that only runs while you're at your
desk, say — by dropping `missed` from its
[`failures`](/configuration/tasks/#failures) list:

```toml
[tasks.daytime-sync]
cron              = "*/30 9-17 * * 1-5"
run               = "/usr/local/bin/sync"
notify = ["slack-ops"]
failures          = ["failed", "timeout", "crashed"]   # real failures still page; missed ticks stay quiet
```

[`failures`](/configuration/tasks/#failures) reclassifies outcomes for stats, the UI, _and_ alerts in one
place — it only changes whether a missed tick counts as a failure, not
whether it's recorded. The `missed` run row is still there and browsable,
so nothing goes invisible. Reach for it instead of hollowing out
[`notify`](/configuration/tasks/#notify), which would also drop your real failure alerts.

## Inline target overrides

Each entry in the list is one of three forms: a bare notifier id
(`"slack-ops"`), the literal `"inapp"`, or an **inline override** of
the form `"<id>:<target>"` that reuses the credentials of the named
notifier but sends to a different target. The override form is useful
when one workspace or one bot serves several destinations — one Slack
workspace covering several channels:

```toml
[notifiers.slack]
type        = "slack"
webhook_url = "${RUNWISP_SLACK_URL}"
# no `channel` set — each task picks one inline

[tasks.nightly-db-backup]
notify = ["slack:#ops"]

[tasks.weekly-deploy]
notify = ["slack:#deploys"]

[services.audit-stream]
notify = ["slack:#audit-alerts"]
```

The form of `<target>` depends on the provider: for Slack it is a
channel (`#name` or `@user`); for Telegram it is the chat id.

```toml
[notifiers.tg]
type      = "telegram"
bot_token = "${RUNWISP_TG_TOKEN}"
chat_id   = "-1001"

[tasks.payments-reconcile]
notify = ["tg:-1009998887"]
```

Notifier ids cannot contain `:` — the colon separates the id from the
target, so `id = "slack:foo"` is rejected at load time. `"inapp"` has
no target and `"inapp:anything"` is rejected. Twenty tasks all writing
`"slack:#ops"` share one connection — `#ops` is not messaged twice
for the same event.

Use an explicit `[notifiers.<id>]` block (with `channel = "#…"` set on
the block itself) when the same channel is used by enough tasks that
the override gets repetitive. Use the inline override when each task
has its own destination.

## When to use a notification rule instead

A per-task field is for one task; a [`[[route]]`
block](/notifications/routes/) is for one rule covering many tasks.
Reach for a rule when you need a pattern across many tasks
(`match.task = "backup-*"`), a custom set of event kinds (the
per-task failure list covers `failed`, [`timeout`](/configuration/tasks/#timeout), `crashed`,
`log_overflow`, `start_failed`, `missed`, and `service.fatal`), or
routing for kinds that have no task — for example
`notify.delivery_failed`. Per-task fields and rules mix freely: the
router collects every channel that matches and sends one message per
unique channel.

## Worked example: per-task field plus a wildcard rule

```toml
[tasks.audit-log]
cron              = "0 0 * * *"
run               = "/usr/local/bin/audit"
notify = ["slack-ops"]

[tasks.process-event-queue]
cron              = "*/10 * * * *"
run               = "/usr/local/bin/process"
notify = ["slack-ops"]

# Backups also send to the on-call channel, in addition to the per-task setting
[[route]]
match     = { kinds = ["failed", "timeout", "crashed"], task = "*-backup" }
notifiers = ["tg-oncall"]
```

A failed `audit-log` run sends one message to `slack-ops` and adds one row
to the bell. A failed `*-backup` run sends one message to `slack-ops`, one
to `tg-oncall`, and adds one row to the bell.

## What the config loader rejects

The loader rejects unknown notifier ids in [`notify`](/configuration/tasks/#notify) (anything that isn't
declared under `[notifiers.*]` and isn't `"inapp"`); inline overrides
whose parent doesn't exist,
whose target is empty, or — for Slack — doesn't start with `#` or
`@`; and `"inapp:something"`. An empty list (`notify = []`)
is fine — it's equivalent to omitting the field, and
`[notify] global_notifiers` still fires.

title: Per-task notifications
description: Use notify_on_failure and notify_on_success on a [tasks.*] or [services.*] block to send notifications when one task ends a certain way.
---

When you only need to alert on one task, put the channel names directly on
that task. The setting lives next to the task definition, so it is easy to
see which task sends to which channel.

Every `[tasks.*]` and `[services.*]` block accepts two fields:

- `notify_on_failure` — send a message when a run ends as `failed`,
  `timeout`, or `crashed`.
- `notify_on_success` — send a message when a run ends as `succeeded`.

They work the same on tasks and services. This page calls the target a
"task" for brevity, but every example applies unchanged to a `[services.*]`
block. The field tables in
[`[tasks.*]`](/configuration/tasks/#notifications) and
[`[services.*]`](/configuration/services/#notifications) list the event
kinds that apply in each context.

Both fields take a list of notifier ids.

## Basic usage

```toml
[tasks.nightly-db-backup]
cron              = "30 2 * * *"
run               = "/usr/local/bin/backup.sh"
notify_on_failure = ["slack-ops"]
```

That is the whole setup. A failed backup sends a message to the `slack-ops`
channel, adds a row to the bell, and is recorded in the notification
history.

## What it does

- `notify_on_failure = ["slack-ops"]` sends one message to `slack-ops` when
  a run of this task ends as `failed`, `timeout`, or `crashed`.
- `notify_on_success = ["slack-ops"]` sends one message to `slack-ops` when
  a run of this task ends as `succeeded`.
- The bell receives the same event by default, because `"inapp"` is in
  `[notify] append_notifiers`. Set `append_notifiers = []` if you want to
  silence the bell — see [Global
  settings](/notifications/global/#the-bell--append_notifiers).
- If a notification rule also matches the same event, each channel still
  receives one message. Duplicates are removed.

## Both fields together

```toml
[services.payments-api]
instances         = 2
run               = "/usr/local/bin/payments-api"
notify_on_failure = ["slack-ops", "tg-oncall"]
notify_on_success = ["slack-ops"]
```

A failure sends to two channels. A clean shutdown sends to one. The two
lists are independent.

## Inline target overrides

Each entry in the list is one of three forms:

- A bare notifier id (`"slack-ops"`) — uses the channel or chat set on the
  notifier itself.
- The literal `"inapp"` — the bell.
- An **inline override**, `"<id>:<target>"` — reuse the credentials from
  the named notifier, but send to a different target for this entry only.

This is useful when one workspace or one bot serves several destinations.
One Slack workspace, several channels:

```toml
[[notifier]]
id              = "slack"
type            = "slack"
webhook_url_env = "RUNWISP_SLACK_URL"
# no `channel` set — each task picks one inline

[tasks.nightly-db-backup]
notify_on_failure = ["slack:#ops"]

[tasks.weekly-deploy]
notify_on_failure = ["slack:#deploys"]
notify_on_success = ["slack:#deploys"]

[services.audit-stream]
notify_on_failure = ["slack:#audit-alerts"]
```

The form of `<target>` depends on the provider. For Slack it is a channel
(`#name` or `@user`). For Telegram it is the chat id:

```toml
[[notifier]]
id            = "tg"
type          = "telegram"
bot_token_env = "RUNWISP_TG_TOKEN"
chat_id       = "-1001"

[tasks.payments-reconcile]
notify_on_failure = ["tg:-1009998887"]
```

A few rules:

- `slack:#ops` reuses the credentials from the `slack` notifier but sends
  to the `#ops` channel.
- **Overrides are deduplicated.** Twenty tasks all writing `"slack:#ops"`
  share one connection — `#ops` is not messaged twice for the same event.
- **Notifier ids cannot contain `:`.** The colon separates the id from the
  target. The config loader rejects `id = "slack:foo"`.
- **`"inapp"` has no target,** so `"inapp:something"` is rejected.

Use an explicit `[[notifier]]` block (with `channel = "#…"` set on the
block itself) when the same channel is used by enough tasks that the
override gets repetitive. Use the inline override when each task has its
own destination.

## When to use a notification rule instead

A per-task field is for one task. A [`[[notification_route]]`
block](/notifications/routes/) is for one rule covering many tasks. Use a
rule when you need any of:

- **A pattern across many tasks.** `match.task = "backup-*"` covers every
  task with the `backup-` prefix in one rule.
- **A custom set of event kinds.** The failure list on the per-task field
  is always `failed + timeout + crashed`. To alert only on `timeout`, use a
  rule.
- **Routing `run.started` or `run.stopped`.** Neither is covered by the
  per-task fields.
- **Routing `notify.delivery_failed`.** It has no task, so the per-task
  field does not apply.
- **Different channels per event kind.** "Channel A on failure, Channel B
  on timeout" needs two separate rules.

You can mix per-task fields and rules freely. The router collects every
channel that matches, removes duplicates, and sends one message per
unique channel.

## Worked examples

### Different settings per task

```toml
[[notifier]]
id              = "slack-ops"
type            = "slack"
webhook_url_env = "RUNWISP_SLACK_OPS_URL"

[tasks.nightly-db-backup]
cron              = "30 2 * * *"
run               = "/usr/local/bin/backup.sh"
notify_on_failure = ["slack-ops"]

[tasks.weekly-deploy]
cron              = "0 9 * * 1"
run               = "/usr/local/bin/deploy.sh"
notify_on_failure = ["slack-ops"]
notify_on_success = ["slack-ops"]   # confirm Mondays went green
```

### Per-task field plus a wildcard rule

```toml
[tasks.audit-log]
cron              = "0 0 * * *"
run               = "/usr/local/bin/audit"
notify_on_failure = ["slack-ops"]

[tasks.process-event-queue]
cron              = "*/10 * * * *"
run               = "/usr/local/bin/process"
notify_on_failure = ["slack-ops"]

# Backups also send to the on-call channel, in addition to the per-task setting
[[notification_route]]
match  = { kind = ["run.failed", "run.timeout", "run.crashed"], task = "*-backup" }
notify = ["tg-oncall"]
```

A failed `audit-log` run sends one message to `slack-ops` and adds one row
to the bell. A failed `*-backup` run sends one message to `slack-ops`, one
to `tg-oncall`, and adds one row to the bell.

## What the config loader rejects

- A notifier id in `notify_on_failure` / `notify_on_success` that is not
  declared in `[[notifier]]` (and is not `"inapp"`).
- An inline override (`"<id>:<target>"`) whose parent is not declared,
  whose target is empty, or — for Slack — does not start with `#` or `@`.
- `"inapp:something"` — the bell has no target.

An empty list (`notify_on_failure = []`) is not rejected — it's
equivalent to omitting the field. `[notify] append_notifiers` still
fires.

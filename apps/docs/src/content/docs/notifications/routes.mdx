title: Notification rules
description: A [[notification_route]] block matches events by kind and task name, and sends them to one or more channels. Use it when one rule should cover many tasks.
---

A `[[notification_route]]` block defines one rule: "when an event matches
this filter, send it to these channels."

If an event matches more than one rule, the router collects every channel
from every match, removes duplicates, and sends one message per unique
channel. Rule order does not change which channels receive the event.

## Shape

```toml
[[notification_route]]
match  = { kind = ["run.failed", "run.timeout", "run.crashed"], task = "backup-*" }
notify = ["slack-ops", "tg-oncall", "inapp"]
```

## Fields

### `match`

| Field            | Type     | Required | What it does                                                                 |
| ---------------- | -------- | -------- | ---------------------------------------------------------------------------- |
| `match.kind`     | string[] | yes      | Event kinds this rule applies to. Empty list matches nothing.                |
| `match.task`     | string   | no       | Shell-style glob on the task name. Omit to match every task.                 |
| `match.severity` | enum     | no       | Threshold: `"info"`, `"warn"`, `"error"`. `warn` matches `warn` and `error`. |

Valid `kind` values:

| Kind                     | Fires when                                                             |
| ------------------------ | ---------------------------------------------------------------------- |
| `run.started`            | A run starts. Opt-in only — not on by default.                         |
| `run.succeeded`          | A run ends with success.                                               |
| `run.failed`             | A run ends with a non-zero exit code.                                  |
| `run.timeout`            | A run is killed for exceeding its `timeout`.                           |
| `run.stopped`            | A run is cancelled (manual stop, or `on_overlap = "terminate"`).       |
| `run.crashed`            | A run is reconciled as crashed after the daemon was killed mid-flight. |
| `notify.delivery_failed` | A notifier exhausted its retries. Delivered only to the bell.          |

The `task` glob uses standard shell-style patterns:

- `*` — any sequence except `/`
- `?` — any single character except `/`
- `[abc]` — one of the listed characters
- **Case-sensitive.** `Backup-*` won't match `backup-db`.
- No brace expansion (`{a,b}` doesn't work).

### `notify`

At least one entry, each one of:

- A `[[notifier]] id` declared elsewhere in the file (e.g. `"slack-ops"`).
- The literal `"inapp"` — the bell. Always available.
- An **inline target override**, `"<id>:<target>"` — reuse a parent
  notifier's credentials but post somewhere else.
  `"slack-ops:#deploys"` reuses the credentials from `slack-ops` and sends
  to the `#deploys` channel for this rule only. The form of `<target>`
  depends on the provider — channel name for some, chat id for others.
  See the provider page. There is also a
  [worked example](/notifications/per-task/#inline-target-overrides).

Notifier ids cannot themselves contain `:` — the colon is reserved for
this separator.

The router deduplicates ids across all matching rules. If two rules both
match an event and both list `slack-ops`, the channel receives one
message.

## Per-task notifications

If you only need to alert on one task, you can put the channel names on
the task itself with `notify_on_failure` / `notify_on_success`:

```toml
[tasks.publish-feed]
notify_on_failure = ["slack-ops"]
notify_on_success = ["slack-ops"]
```

See [Per-task notifications](/notifications/per-task/) for the full
behaviour. Both forms can be used in the same config; the router removes
duplicate channels.

## Delivery failures

When an outbound notifier exhausts its retry budget, the daemon emits a
`notify.delivery_failed` event. To stop a channel outage from causing more
delivery attempts on the same channel, this event is sent **only to the
bell** — never through the outbound router.

You can still route delivery failures through a _different_ channel
yourself, since the router treats `notify.delivery_failed` as a valid
`match.kind`:

```toml
# If one channel is down, route delivery failures to a different one
[[notification_route]]
match  = { kind = ["notify.delivery_failed"] }
notify = ["tg-oncall"]
```

The bell-only delivery happens regardless of this rule — it is the
always-safe fallback.

## Worked example

```toml
# Every failed/timeout/crashed run is sent to the team channel
[[notification_route]]
match  = { kind = ["run.failed", "run.timeout", "run.crashed"] }
notify = ["slack-ops"]

# Backups also send to the on-call channel
[[notification_route]]
match  = { kind = ["run.failed", "run.timeout", "run.crashed"], task = "backup-*" }
notify = ["tg-oncall"]

# Send delivery failures only to the bell — they are often the channel's own outage
[[notification_route]]
match  = { kind = ["notify.delivery_failed"] }
notify = ["inapp"]
```

A failure of `backup-postgres` sends one message to `slack-ops`, one
message to `tg-oncall`, and adds one row to the bell (added by
`append_notifiers`). A failure of `metrics-export` sends one message to
`slack-ops` and adds one row to the bell.

## What the config loader rejects

- A route referencing a notifier `id` not declared in `[[notifier]]`
  (and not `"inapp"`).
- An empty `notify` list.
- A `match.kind` value that isn't one of the seven listed above.
- A `match.task` glob that can't be parsed (e.g. unmatched `[`).
- An inline override (`"<id>:<target>"`) whose parent isn't declared,
  whose target is empty, or — for Slack — doesn't start with `#` or
  `@`. `"inapp:something"` is also rejected (the bell has no target).
- A `[[notifier]] id` containing `:`.

Every key a `[tasks.<name>]` block accepts, with its type, default, and accepted

built-in default.

## Identity & metadata

### `[tasks.<name>]`

**type**: `string` **required**

Whatever follows `tasks.` is the task's name - `[tasks.backup-db]` defines a task
called `backup-db`. It shows up in the Web UI, TUI, API, CLI and the log directory.

Allowed characters are letters, digits, and `. _ - :`, up to 100 characters.

`[tasks.*]` and [`[services.*]`](/configuration/services/) share one
namespace - the name must be unique across both of them.

If you need `.` or `:` in the task name, use quotes (`[tasks."db:backup"]`)

```toml
[tasks.backup-db]
run = "pg_dump app | gzip > /backups/app.sql.gz"

[tasks."db:backup"]  # quotes required: not a bare TOML key
run = "..."
```

## Scheduling

### cron

**type**: `string`

When the task runs, written as cron. Leave it off and the task runs only when
triggered by hand. Accepts 5 fields (`min hour day month weekday`), or 6 with a
leading seconds field for sub-minute precision, plus `@`-shorthands.

```toml
[tasks.healthcheck]
cron = "*/30 * * * * *" # every 30s, aligned to :00 and :30
run  = "curl -fsS http://localhost:8080/healthz"
```

Possible values:

- `*/5 * * * *`: every 5 minutes
- `0 3 * * *`: every day at 03:00
- `0 9 * * 1-5`: 09:00 Monday to Friday
- `*/30 * * * * *`: every 30 seconds (6-field, leading seconds)
- `@hourly`, `@daily`: shorthand forms
- `@every 1h30m`: fixed interval, ignores wall-clock alignment

[How scheduling works](/concepts/scheduling/) has the full cron grammar, the DST
behaviour, and the catch-up details.

:::tip[Catch mistakes before deploy]
`runwisp validate` runs the exact same checks as daemon boot. A bad cron
expression, a misspelled key, or a duration like `"5 minutes"` instead of `"5m"`
all fail with an actionable message.
:::

### timezone

**type**: `string` **default**: `[scheduler] timezone`, then the host zone

The IANA zone this task's cron is read in. Use it when one job must run on a
different region's clock than the rest.

```toml
[tasks.eu-market-open]
cron     = "0 9 * * 1-5"
timezone = "Europe/Bratislava"
```

### jitter

**type**: `duration`

Cap how far this task's start may slip so tasks sharing a fire time take turns
instead of stampeding together. It's a ceiling, not a fixed offset — on a quiet
daemon with nothing else jittered in flight, the task starts right on the tick.
Needs a `cron`; it's a no-op on a manual-only task, and manual triggers, retries,
and catch-up runs never wait on it.

```toml
[tasks.nightly-report]
cron   = "0 3 * * *"
jitter = "30m"  # start may slip up to 30m while other jittered runs are busy
```

Set it once in [`[defaults]`](/configuration/defaults/) to pace the whole
schedule at once.

### catch_up

**type**: `integer` **default**: `1` **min**: `0` **max**: `10000`

How many missed cron ticks to re-fire on startup after downtime. `0` skips
the backlog, `1` re-runs only the most recent missed tick, `N` replays up to
the `N` most recent. Above `1` requires `on_overlap = "queue"` — the runtime
replays missed ticks back-to-back, which only lands every replay when
`queue` serializes them; `skip`/`kill` would let only the first one through.

```toml
[tasks.hourly-roll]
cron       = "0 * * * *"
catch_up   = 24
on_overlap = "queue"
```

### run_on_start

**type**: `boolean` **default**: `false`

Run the task once, right after the daemon starts — on top of any `cron`.
Independent of `catch_up`, and doesn't count against it; tagged
`triggered_by = startup` in run history. The equivalent of cron's `@reboot`.

```toml
[tasks.warm-cache]
run_on_start = true
run          = "/usr/local/bin/warm-cache"
```

## Concurrency

### max_concurrent

**type**: `integer` **default**: `1` **min**: `1` **max**: `1024`

How many runs of this task may be active at once. At the limit,
[on_overlap](#on_overlap) decides what happens to the next trigger.

```toml
[tasks.thumbnailer]
max_concurrent = 4
```

### on_overlap

**type**: `enum` **default**: `"queue"`

What happens when the task is triggered while already at
[max_concurrent](#max_concurrent) (default `1`).

```toml
[tasks.queue-drain]
cron       = "*/10 * * * *"
on_overlap = "skip"
```

Possible values:

- `queue`: the new run waits and starts when a slot frees up (bounded by [max_queued](#max_queued))
- `skip`: the new run is dropped and recorded as skipped
- `kill`: the running run is stopped so the new one takes over

### max_queued

**type**: `integer` **default**: `100` **min**: `0` **max**: `10000`

With `on_overlap = "queue"`, the cap on runs waiting in line. Past the cap,
further triggers record `end_reason = "queue_full"`.

```toml
[tasks.ingest]
on_overlap = "queue"
max_queued = 500
```

## Retries & timeout

### retry_attempts

**type**: `integer` **default**: `0` **min**: `0` **max**: `100`

Extra attempts after the first one fails. Retries fire on `failed`, `timeout`,
`crashed`, `log_overflow`, and `start_failed`; a manual stop or a kill ends the
chain.

```toml
[tasks.flaky-fetch]
retry_attempts = 3
retry_delay    = "2s"
```

### retry_delay

**type**: `duration` **default**: `5s`

The base wait between retry attempts. Only consulted when `retry_attempts` is
above `0`; `retry_backoff` decides how it grows.

```toml
[tasks.flaky-fetch]
retry_attempts = 3
retry_delay    = "5s"
```

### retry_backoff

**type**: `enum` **default**: `"constant"`

How `retry_delay` grows across attempts.

```toml
[tasks.flaky-fetch]
retry_attempts = 4
retry_delay    = "2s"
retry_backoff  = "exponential"  # 2s, 4s, 8s, 16s
```

Possible values:

- `constant`: the same `retry_delay` before every attempt
- `linear`: `retry_delay` times the attempt number (2s, 4s, 6s)
- `exponential`: double each time (2s, 4s, 8s, 16s)

### timeout

**type**: `duration` **default**: none (no limit)

A per-attempt wall-clock cap. A run that runs longer is stopped through the
stop-signal ladder and recorded as `timeout`. Inherits `[defaults]` when unset.

```toml
[tasks.queue-drain]
cron    = "*/10 * * * *"
timeout = "9m"
```

### Fail-fast

RunWisp invokes `run` as `<shell> -e -c <script>`, so a multi-line script stops
at the first command that fails, and that command's exit code becomes the run's
— you don't write `set -e` yourself.

`-u` (error on unset variables) and `-o pipefail` are deliberately left off:
`-u` breaks scripts that read optional env vars, and `-o pipefail` isn't POSIX
(dash rejects it). To catch a failing upstream in a pipe, set [shell](#shell) to
`/bin/bash` and write `set -o pipefail` yourself.

To disable fail-fast for one task, make `set +e` the first line of `run`. For a
single command expected to exit non-zero, end it with `|| true` instead.

## What counts as a failure

:::note[The failure model]
Every run ends with a reason. `failures` decides which reasons (and exit codes)
turn a run red and fire `notify`.

- A token is a reason name or an exit code / inclusive range (`"42"`, `"1-23"`;
  codes are 1–255, exit `0` is always success).
- List `"failed"` and every non-zero exit is a failure. Omit it and only the
  codes you list fail; every other non-zero exit stays neutral — recorded,
  visible, but not red and not paged.
- A bare list replaces the inherited set; prefix every token with `+` or `-` to
  adjust it instead. The two styles can't be mixed in one list.

It's purely an observability choice — it never changes retries, which always
fire on `failed`, `timeout`, `crashed`, `log_overflow`, and `start_failed`.
:::

### failures

**type**: `string[]` **default**: `["failed", "timeout", "crashed", "log_overflow", "start_failed", "missed"]`

Which run outcomes count as a failure.

```toml
[tasks.web]
failures = ["-missed"]              # stop paging on a missed tick

[tasks.rsync]
failures = ["timeout", "23", "24"]  # only these exits fail
```

Possible values:

- `failed`: the command exited non-zero
- `timeout`: killed for running past [timeout](#timeout)
- `crashed`: died on a signal (OOM-killed, segfault)
- `log_overflow`: hit [log_max_size](#log_max_size) under `log_on_full = "kill"`
- `start_failed`: the process could not be started
- `missed`: a scheduled firing was skipped while the daemon was down
- `stopped`: an operator stopped the run
- `daemon_stopped`: still running when the daemon shut down

## Parameters

New to parameters? The [Parameters concept guide](/concepts/parameters/) is the
friendlier introduction — this section is the exhaustive key reference.

### params

**type**: `table` (array of `[[tasks.<name>.params]]` entries)

Declare the inputs a task takes. Each one becomes a field on the Web UI, TUI,
and REST Run Task form, so an operator can fill it in per run. Every entry sets
exactly one identity keyword (`env`/`arg`/`option`/`flag`), which decides how
the value reaches your command. Values always arrive as real argv entries or
env vars, never spliced into the shell string, so an operator typing
`; rm -rf /` gets an inert string. Scheduled runs (cron, catch-up, retries) use
the declared defaults.

```toml
[tasks.backup]
run = "/usr/local/bin/backup.sh"
params = [
  { env = "PROJECT_ID", required = true },
  { arg = "source", required = true },
  { arg = "dest", default = "/backups" },
  { option = "--region", choices = ["us", "eu"] },
  { flag = "--force" },
]
```

Identity keyword (exactly one per entry):

- `env`: expose the value as an environment variable of that name. Can't collide
  with a static `env`/`secrets` key on the same task.
- `arg`: append the value as a positional argument, in declaration order.
- `option`: render as `--name value`. A name ending in `=` glues them
  (`--date=2026-01-01`).
- `flag`: a boolean whose token is appended when on, omitted when off. Takes no
  `choices` or `type`.

Attributes:

- `default`: value scheduled runs use and manual forms pre-fill (`true`/`false`
  for a flag). A parameter with a `default` is safe on a scheduled task.
- `required`: the manual form won't submit without a value
  (`env`/`arg`/`option`). A required parameter on a scheduled task must also
  set `default`.
- `type`: `string` (default) or `number`; a `number` that doesn't parse is
  rejected before the run starts.
- `choices`: restrict to a fixed list, shown as a dropdown. Values outside it
  are rejected.
- `allow_custom`: with `choices`, also let the operator type a value not in the
  list. Meaningless (and rejected) without `choices`.
- `description`: help text shown under the field.

:::note[Omitting a value vs. passing an empty one]
When you trigger a task by hand, clearing a field and passing an empty string
differ.

- Leave a field as-is and its value (the default, or what you typed) is
  passed.
- Clear it and the parameter is omitted: the option, arg, or env var isn't
  passed at all. Clearing does not fall back to the default; a `required`
  field can't be omitted.
- Pass an empty string when your program distinguishes `--note ''` from no
  `--note`: use the toggle under the field (in the TUI, <kbd>ctrl+t</kbd>).

Flags have no ambiguity: off means the token isn't appended. Scheduled runs and
retries use the declared defaults, and a retry replays exactly what the
original run was given.
:::

## Compose-backed tasks

A cron-driven `[tasks.<name>]` can also point at a compose service for
one-shot runs:

```toml
[tasks.nightly-backup]
cron            = "0 3 * * *"
compose_file    = "./docker-compose.yml"
compose_service = "backup"
```

<ComposeMode />

For importing every service in a compose file as observable RunWisp services,
see [`[compose.*]`](/configuration/compose/).

:::note[Parameters on a compose task]
[Parameters](#params) work here, with one difference in fresh-container mode
(`compose_file` and `compose_service`, no `run`): `arg`, `option`, and `flag`
values go to the container the way `docker compose run <svc> …` passes them,
replacing the service's `command:` and arriving as arguments to the image's
`ENTRYPOINT`.

```toml
[tasks.nightly-backup]
cron            = "0 3 * * *"
compose_file    = "./docker-compose.yml"
compose_service = "backup"
params          = [{ arg = "since", default = "yesterday" }]
```

:::

## What's rejected on tasks

The config loader turns these away at startup, so they can't quietly bite you
later:

- `restart` / `restart_attempts` — services-only; a task re-runs a failed run with `retry_attempts`/`retry_delay`/`retry_backoff`, not restart.
- `instances = N` — a services-only field.
- `priority` / `autostart` — services-only; they govern boot start order and whether a service comes up at boot.
- `depends_on` — services-only; it gates a service's boot on other services being healthy.
- A task name that's also taken by a `[services.*]` — they share one namespace.
- An empty or missing `run` (unless [compose_file](#compose_file) is set).

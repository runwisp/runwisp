A service is an always-on process that RunWisp works to keep alive — it exits
or crashes, it gets restarted, until you stop it. Every key a
`[services.<name>]` block accepts, with its type, default, and accepted
values. Unset keys fall back to [`[defaults]`](/configuration/defaults/), then
a built-in default.

## Identity & metadata

### `[services.<name>]`

**type**: `string` **required**

Whatever follows `services.` is the service's name — `[services.api-worker]`
defines a service called `api-worker`. It shows up in the CLI, API, Web UI,
and the log directory. Names use letters, digits, and `. _ - :`, up to 100
characters, and are unique across `[services.*]` and
[`[tasks.*]`](/configuration/tasks/) — they share one namespace. Quote
anything that isn't a bare TOML key.

```toml
[services.api-worker]
run = "/usr/local/bin/worker"
```

### manual_trigger

<ManualTrigger />

Restart is the usual interaction for a service — the button that starts a
stopped one back up. Set `manual_trigger = false` if you don't want anyone
stopping or restarting this service by hand, from any front door: the
**Stop Service** button, TUI `s`/`r`, `runwisp service stop/restart`, the
REST API, and the station control plane all refuse it; only a
`runwisp.toml` edit plus `runwisp reload` changes its running state.

## Instances

### instances

**type**: `integer` **default**: `1` **min**: `1` **max**: `64`

Number of concurrent instances. Each shows up as its own run, tagged with its
own `instance_index` (`0`, `1`, `2`, …); the Web UI and TUI label them
`name#1`, `name#2`, and a single-instance service stays just `name`. They
share the same config, pool their logs together, and when one instance's
process exits the supervisor restarts just that one.

```toml
[services.api-worker]
instances = 3
run       = "/usr/local/bin/worker"
```

## Restart behaviour

`restart = "always"` is baked in and **can't be overridden** — that's the deal
with a service. If what you want is "run once and exit," that's a
[task](/concepts/tasks-vs-services/).

### restart_delay

**type**: `duration` **default**: `1s`

Base delay between automatic restarts after a process exits on its own. An
explicit `0` (or `"0s"`) is kept exactly as written — never silently replaced
by the default; only omitting the key falls back to `[defaults]`. Hitting
**Restart** by hand skips the delay entirely.

```toml
[services.flaky]
restart_delay = "2s"
```

### restart_backoff

**type**: `enum` **default**: `"exponential"`

Curve applied to `restart_delay` (shared with task `retry_backoff`): `constant`,
`linear`, or `exponential`. The backoff has a ceiling, so even a long stretch
of flapping won't push the delay forever upward.

```toml
[services.flaky]
restart_backoff = "exponential"
```

### healthy_after

**type**: `duration` **default**: inherited (built-in `60s`)

Uptime an instance must reach to count as healthy — resets its restart
backoff **and** clears the failed-start streak used by `restart_attempts`.
Exits faster than this with a failure count as a failed start.

```toml
[services.api-worker]
healthy_after = "2m"  # this one needs longer to call "stable"
```

### restart_attempts

**type**: `integer` **default**: `3` **min**: `0` **max**: `100`

Consecutive failed starts an instance tolerates before it's marked **FATAL**
and stops restarting. `0` means give up after the very first failed start.

```toml
[services.flaky]
restart_attempts = 2
```

### When a service can't start: FATAL

Restarting forever is right for a service that _occasionally_ falls over. It's
wrong for one that can _never_ start — a typo in the command, a missing
binary, a bad config. Without a backstop that service would flap silently
until you happened to look.

Every time an instance exits, RunWisp checks how long it stayed up. Reach
`healthy_after` and the failed-start counter resets to zero. Exit _faster_
than `healthy_after` with a failure (a clean exit on a success code never
counts), and that's a failed start. Rack up more than `restart_attempts`
failed starts in a row and the instance goes **FATAL**: it stops restarting, a
`start_failed` run is recorded, and a `service.fatal` notification lights the
in-app bell and any configured [notifiers](/notifications/model/).

FATAL lives in memory only. Restarting the daemon, or hitting **Restart** on
the service in the UI/API, gives it a fresh `restart_attempts` budget and
tries again. The `start_failed` runs stay in history either way.

```toml
[services.flaky]
run              = "exit 1"   # can never come up
healthy_after    = "5s"       # must stay up 5s to count as healthy
restart_attempts = 2          # give up after 2 failed starts in a row
```

## Startup

### priority

**type**: `integer` **default**: `0`

Boot start order across services — lower starts first, ties break on name.
This is start order **only**: it's not a readiness gate, it just fixes the
otherwise-random spawn order. If one service needs another to actually be
_up_ first, that's [`depends_on`](#depends_on).

```toml
[services.db]
priority = 0

[services.api]
priority = 10
```

### autostart

**type**: `boolean` **default**: `true`

Whether the service comes up at boot. `false` boots it stopped until you
start it from the UI/API — for a maintenance worker or a one-off runner you
trigger by hand. This desired state isn't persisted: it's re-read from
`runwisp.toml` every boot, so a manually started `autostart = false` service
is stopped again after a restart, and a manually stopped `autostart = true`
service comes back up.

```toml
[services.migration-runner]
autostart = false
```

## Boot order with `depends_on`

### depends_on

**type**: `string[]` **default**: none

Other **services** that must be healthy before this one starts at boot.
Order only.

```toml
[services.db]
run           = "postgres -D /var/lib/pg"
healthy_after = "3s"      # call it "up" once it stays alive 3s

[services.api]
run        = "./api-server"
depends_on = ["db"]       # wait for db to be healthy, then start
```

At boot, `api` waits until `db` reports healthy — at least one `db` instance
has stayed live for its [`healthy_after`](#healthy_after) window — and only
then starts. A service can depend on several at once. A few rules worth
knowing:

- **It never deadlocks your boot.** If a dependency never becomes healthy, the
  dependent waits a bounded window and then **starts anyway, with a loud
  warning in the log**.
- **Manual start/restart is ungated.** `depends_on` only gates the automatic
  boot.
- **Shutdown reverses it.** Dependents stop before the services they depend
  on.
- **Cycles are rejected at load**, and references must point at services (not
  tasks) that actually exist.

This is deliberately small — boot ordering and a readiness gate, nothing
more. It is **not** [orchestration](/concepts/tasks-vs-services/): no cascade
restarts, no run-to-completion edges, no data passing.

## Concurrency

Services have no `on_overlap` — that's a `[tasks.*]` knob. A service's
instance count is fixed by [`instances`](#instances), and the supervisor
holds that count steady on its own, so there's nothing to configure:
there's no "run" to overlap with, only instances to keep alive. There's
no `max_concurrent` or `max_queued` either, for the same reason.

## Compose-backed services

`[services.<name>]` can run a service defined in an existing
`docker-compose.yml` instead of a raw shell command:

```toml

compose_file    = "./docker-compose.yml"
compose_service = "api"
notify = ["slack-prod"]
```

## Notifications

### notify

<Notify />

An instance's `notify` fires when it ends `failed`, `crashed`, `timeout`, or
`missed`, or when a slot goes `fatal` — reaching the exact same channels a
failed `[tasks.*]` run would.

## Cooperating with `graceful_stop`

The practical advice: trap `SIGTERM` in your `run` command and exit cleanly.
The starter file's pattern is a fine place to begin:

```bash
trap 'echo "SIGTERM — shutting down"; exit 0' TERM INT
while true; do
  # do work
done
```

An instance that catches `SIGTERM` and exits cleanly is recorded with
`end_reason = stopped`.

## What's rejected on services

- `cron`, `catch_up` — services aren't cron-driven.
- [`params`](/configuration/tasks/#parameters) — services don't take per-execution parameters.
- `retry_attempts`, `retry_delay`, `retry_backoff` — services restart instead of retry. Use `restart_delay` / `restart_backoff`.
- `on_overlap`, `max_concurrent`, `max_queued` — instance count is `instances`; services don't queue or overlap.
- A name shared with a `[tasks.*]` entry.
- Empty or missing `run`.
- `instances` outside `[1, 64]`.

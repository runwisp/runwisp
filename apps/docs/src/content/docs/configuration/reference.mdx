<div class="rw-config-ref" />

Every key a `[tasks.<name>]` block accepts, with its type, default, and accepted
values. `runwisp.toml` is the source of truth for task definitions: the REST API
and Web UI are read-only. Unset keys fall back to `[defaults]`, then to a built-in
default.

Two commands inspect a config without running it:

```bash
# validate runwisp.toml and print a summary, or a structured error
runwisp validate

# print the full runwisp.toml JSON Schema (draft 2020-12) to stdout
runwisp schema
```

The narrative pages ([tasks](/configuration/tasks/), [defaults](/configuration/defaults/))
cover the _why_ and _when_. This page is the exhaustive _what_. Use your browser's
find (Ctrl-F) or the "On this page" list to jump to a key.

## Identity & metadata

### `<name>`

**type**: `string` **required**

Whatever follows `tasks.` is the task's name: `[tasks.backup-db]` defines a task
called `backup-db`. That name shows up in the CLI, API, Web UI, and the folder its
logs go to.

Use letters, digits, and `. _ - :`, under 100 characters. Names are unique across
tasks and services. Quote anything that isn't a bare TOML key.

A task needs only its table header and a [run](#run); everything else inherits from
`[defaults]` or a built-in default.

```toml
[tasks.backup-db]
run = "pg_dump app | gzip > /backups/app.sql.gz"

[tasks."db:backup"]  # quotes required: not a bare TOML key
run = "..."
```

### run

**type**: `string` **required** (unless [compose_file](#compose_file) is set)

The shell command the task runs. It executes under `/bin/sh -e -c`, so the first
command that fails stops the run and its exit code becomes the run's. Switch
[shell](#shell) to bash for arrays or `pipefail`.

On a compose-backed task, `run` is optional: set it to run that command inside the
service's container (see [compose_mode](#compose_mode)).

```toml
[tasks.heartbeat]
cron = "*/5 * * * *"
run  = "curl -fsS https://example.com/health"
```

Possible values:

- `/usr/local/bin/backup.sh`: a script on disk
- `pg_dump app | gzip > /backups/app.sql.gz`: a shell pipeline
- `make -C /srv/app deploy`: any command on your `PATH`

### description

**type**: `string`

A short line shown next to the task in the Web UI and TUI. It never affects
scheduling or execution.

```toml
[tasks.backup]
description = "Nightly Postgres dump to S3"
```

### group

**type**: `string` **default**: `"Tasks"`

The section this task appears under in the Web UI and TUI sidebar. Give several
tasks the same group to file them together.

```toml
[tasks.nightly-report]
group = "Reports"
```

### manual_trigger

**type**: `boolean` **default**: `true`

Whether operators can start this task by hand. Set `false` to lock it to its
schedule: the REST API returns 403, the Web UI hides its Run button, the cloud
trigger is refused. Scheduling (cron, retries, catch-up, overlap) is unaffected.

```toml
[tasks.nightly-merge]
cron           = "0 4 * * *"
manual_trigger = false  # only the scheduler may start it
```

## Scheduling

### cron

**type**: `string`

When the task runs, written as cron. Omit it and the task runs only when triggered
by hand. Accepts 5 fields, or 6 for leading seconds, plus `@`-shorthands.

```toml
[tasks.healthcheck]
cron = "*/30 * * * * *"  # every 30s, aligned to :00 and :30
run  = "curl -fsS http://localhost:8080/healthz"
```

Possible values:

- `*/5 * * * *`: every 5 minutes
- `0 * * * *`: top of every hour
- `0 3 * * *`: every day at 03:00
- `0 9 * * 1-5`: 09:00 Monday to Friday
- `*/30 * * * * *`: every 30 seconds (6-field, leading seconds)
- `@hourly`: shorthand for `0 * * * *`
- `@daily`: shorthand for midnight every day
- `@every 1h30m`: fixed interval, ignores wall-clock alignment

### timezone

**type**: `string` **default**: `[scheduler] timezone`, then the host zone

The IANA zone this task's cron is read in. Use it when one job must run on a
different region's clock than the rest.

```toml
[tasks.eu-market-open]
cron     = "0 9 * * 1-5"
timezone = "Europe/Bratislava"
```

Possible values:

- `Europe/Bratislava`: central European time
- `America/New_York`: US eastern time
- `Asia/Shanghai`: all of China, Beijing time (no DST)

### jitter

**type**: `duration`

The longest RunWisp will hold a cron task's start back to avoid a thundering herd.
The delay applies only when another jittered task is already running, so on a quiet
machine the task starts on time. Does nothing without a `cron`. Set it in
`[defaults]` to spread the whole schedule.

```toml
[tasks.nightly-report]
cron   = "0 3 * * *"
jitter = "30m"  # up to 30m late, only when other jittered tasks run
```

### catch_up

**type**: `enum` **default**: `"latest"`

What to do about scheduled runs missed while RunWisp (or the server) was down.

```toml
[tasks.hourly-roll]
cron       = "0 * * * *"
catch_up   = "all"
on_overlap = "queue"
```

Possible values:

- `latest`: run the most recent missed firing once, then resume
- `all`: replay every missed firing in order (requires [on_overlap](#on_overlap) `= "queue"`, capped by [max_catch_up_runs](#max_catch_up_runs))
- `skip`: discard the backlog, wait for the next scheduled run

### max_catch_up_runs

**type**: `integer` **default**: `100` **min**: `1` **max**: `10000`

The cap on how many missed firings [catch_up](#catch_up) `= "all"` replays. Only
consulted when `catch_up` is `"all"`; older firings past the cap are dropped.

```toml
[tasks.hourly-roll]
catch_up          = "all"
on_overlap        = "queue"
max_catch_up_runs = 24  # at most a day's worth
```

### run_on_start

**type**: `boolean` **default**: `false`

Run the task once, right after the daemon starts. With a [cron](#cron), it fires at
startup and then keeps its schedule; without one, it runs only at startup. The
equivalent of cron's `@reboot`.

```toml
[tasks.warm-cache]
run_on_start = true
run          = "/usr/local/bin/warm-cache"
```

## Concurrency

### max_concurrent

**type**: `integer` **default**: `1` **min**: `1` **max**: `1024`

How many runs of this task may be active at once. At the limit,
[on_overlap](#on_overlap) decides what happens to the next trigger.

```toml
[tasks.thumbnailer]
max_concurrent = 4
```

### on_overlap

**type**: `enum` **default**: `"queue"`

What happens when the task is triggered while already at its
[max_concurrent](#max_concurrent) limit (default `1`).

```toml
[tasks.queue-drain]
cron       = "*/10 * * * *"
on_overlap = "skip"
```

Possible values:

- `queue`: the new run waits and starts when a slot frees up (bounded by [max_queued](#max_queued))
- `skip`: the new run is dropped and recorded as skipped
- `kill`: the running run is stopped so the new one takes over

### max_queued

**type**: `integer` **default**: `100` **min**: `0` **max**: `10000`

With [on_overlap](#on_overlap) `= "queue"`, the cap on runs waiting in line. At the
cap, further triggers fail with a "Queue full" status.

```toml
[tasks.ingest]
on_overlap = "queue"
max_queued = 500
```

## Retries & timeout

### retry_attempts

**type**: `integer` **default**: `0` **min**: `0` **max**: `100`

Extra attempts after the first one fails. Retries fire on `failed`, `timeout`,
`crashed`, `log_overflow`, and `start_failed`; a manual stop or a kill ends the
chain. See [retry_delay](#retry_delay) and [retry_backoff](#retry_backoff) for the
timing.

```toml
[tasks.flaky-fetch]
retry_attempts = 3
retry_delay    = "2s"
```

### retry_delay

**type**: `duration` **default**: `5s`

The base wait between retry attempts. Used only when
[retry_attempts](#retry_attempts) is above `0`; [retry_backoff](#retry_backoff)
decides how it grows.

```toml
[tasks.flaky-fetch]
retry_attempts = 3
retry_delay    = "5s"
```

### retry_backoff

**type**: `enum` **default**: `"constant"`

How [retry_delay](#retry_delay) grows across attempts.

```toml
[tasks.flaky-fetch]
retry_attempts = 4
retry_delay    = "2s"
retry_backoff  = "exponential"  # 2s, 4s, 8s, 16s
```

Possible values:

- `constant`: the same `retry_delay` before every attempt
- `linear`: `retry_delay` times the attempt number (2s, 4s, 6s)
- `exponential`: double each time (2s, 4s, 8s, 16s)

### timeout

**type**: `duration` **default**: none (no limit)

A per-attempt wall-clock cap. A run that runs longer is stopped through the
[stop_signal](#stop_signal), then [graceful_stop](#graceful_stop), then SIGKILL
ladder, and recorded as `timeout`. Inherits `[defaults]` when unset.

```toml
[tasks.queue-drain]
cron    = "*/10 * * * *"
timeout = "9m"
```

:::note[Fail-fast]
A multi-line `run` executes under `<shell> -e -c`, so it stops at the first command
that fails, and that command's exit code becomes the run's. RunWisp arms `-e` for
you: you don't write `set -e`.

Two things it deliberately leaves off:

- `-u` (error on unset variables) breaks scripts that read optional env vars. Write
  `set -u` yourself if you want it.
- `-o pipefail` isn't POSIX (dash rejects it). To catch a failing upstream in a
  pipe, set [shell](#shell) to `/bin/bash` and write `set -o pipefail`.

To disable fail-fast for one task, make `set +e` the first line of its `run`. For a
single command expected to exit non-zero, end it with `|| true`.
:::

### graceful_stop

**type**: `duration` **default**: `5s`

How long a stopping run gets to exit cleanly after the [stop_signal](#stop_signal),
before RunWisp SIGKILLs it. Applies on timeout, an `on_overlap = "kill"`, a manual
stop, and shutdown, and covers the whole process group. Set `"0s"` to kill
immediately.

```toml
[tasks.queue-drain]
graceful_stop = "30s"
```

### stop_signal

**type**: `enum` **default**: `"SIGTERM"`

The signal that opens the stop ladder (the `SIG` prefix is optional). Use `SIGINT`
for tools that treat it like Ctrl-C, or `SIGKILL` to skip the grace window.
Anything still alive after [graceful_stop](#graceful_stop) is SIGKILLed regardless.

```toml
[tasks.worker]
stop_signal   = "SIGINT"
graceful_stop = "10s"
```

Possible values: `SIGTERM`, `SIGINT`, `SIGQUIT`, `SIGHUP`, `SIGKILL`, `SIGUSR1`,
`SIGUSR2` (or the same names without the `SIG` prefix).

## What counts as a failure

:::note[The failure model]
Every run ends with a reason. `failures` decides which reasons (and exit codes)
turn a run red and page you.

- A token is a reason name or an exit code / inclusive range (`"42"`, `"1-23"`;
  codes are 1 to 255, exit 0 is always success).
- List `"failed"` and every non-zero exit is a failure. Omit it and only the codes
  you list fail; every other non-zero exit stays neutral (recorded and visible, but
  not red and not paged).
- A bare list replaces the inherited set; prefix every token with `+` or `-` to
  adjust it instead. The two styles can't be mixed in one list.

It's purely an observability choice. It never changes retries, which always fire on
`failed`, `timeout`, `crashed`, `log_overflow`, and `start_failed`.
:::

### failures

**type**: `string[]` **default**: `["failed", "timeout", "crashed", "log_overflow", "start_failed", "missed"]`

Which run outcomes count as a failure. Each token is a reason name or an exit
code / range. See the failure model above for the `+`/`-` adjust syntax.

```toml
[tasks.web]
failures = ["-missed"]              # stop paging on a missed tick

[tasks.rsync]
failures = ["timeout", "23", "24"]  # only these exits fail
```

Possible values:

- `failed`: the command exited non-zero
- `timeout`: killed for running past [timeout](#timeout)
- `crashed`: died on a signal (OOM-killed, segfault)
- `log_overflow`: hit [log_max_size](#log_max_size) under `log_on_full = "kill"`
- `start_failed`: the process could not be started
- `missed`: a scheduled firing was skipped while the daemon was down
- `stopped`: an operator stopped the run
- `daemon_stopped`: still running when the daemon shut down
- `"42"`: one exit code
- `"1-23"`: an inclusive exit-code range

## Logs & retention

### log_max_size

**type**: `size` **default**: `100mb`

The cap on one run's captured stdout/stderr on disk. Units are `b`/`kb`/`mb`/`gb`/`tb`.
At the cap, [log_on_full](#log_on_full) decides what happens. `0`, negatives, and
malformed strings are rejected at load.

```toml
[tasks.chatty-job]
log_max_size = "500mb"
```

### log_on_full

**type**: `enum` **default**: `"drop_old"`

What to do when a run's log reaches [log_max_size](#log_max_size).

```toml
[tasks.verbose-import]
log_max_size = "50mb"
log_on_full  = "drop_old"
```

Possible values:

- `drop_old`: keep the newest output, discard the oldest
- `drop_new`: freeze the log at the earliest output, ignore the rest
- `kill`: stop the run and record `log_overflow`

### keep_runs

**type**: `integer` **min**: `0` **max**: `1000000`

Keep only the N most recent completed runs; older rows and their logs are trimmed on
the hourly cleanup. Inherits `[defaults]` when unset; `0` keeps no completed runs.
Set alongside [keep_for](#keep_for), and whichever trims more wins.

```toml
[tasks.noisy-poller]
keep_runs = 200
```

### keep_for

**type**: `duration`

Delete runs older than this age. Unlike most durations, `keep_for` also accepts `d`
(days) and `w` (weeks). Inherits `[defaults]` when unset; combine with
[keep_runs](#keep_runs) and the stricter limit wins.

```toml
[tasks.audit]
keep_for = "90d"
```

Possible values:

- `48h`: 2 days
- `14d`: 14 days (`d` is retention-only)
- `2w`: 2 weeks (`w` is retention-only)
- `90d`: about 3 months

## Environment & secrets

:::note[How env & secrets merge]
All four layers merge on top of the daemon's own environment; on a key collision,
later wins.

- The daemon process's own environment (the base).
- [env_file](#env_file), then [env](#env): the file merges beneath the inline map,
  so inline entries win.
- [secrets_file](#secrets_file), then [secrets](#secrets): same rule.
- Secrets sit above plain env, so a secret always beats a same-named public value.

`env` and `secrets` reach the process the same way. The difference is visibility:
`env`/`env_file` values sit in the open in the API, UI, and CLI, while
`secrets`/`secrets_file` never leave the daemon (at most you see the `secrets_file`
path). All of it is validated at load: keys match `^[A-Za-z_][A-Za-z0-9_]*$`, no NUL
bytes, no value over 32 KiB, at most 256 entries per task.
:::

### env

**type**: `map`

Environment variables injected into the process. For non-secret values only.
Passwords, tokens, and anything you wouldn't want shown in the API or UI go in
[secrets](#secrets). To read from a file, use [env_file](#env_file).

```toml
[tasks.backup.env]
BACKUP_BUCKET = "s3://prod-backups"
DRY_RUN       = "0"
```

### secrets

**type**: `map`

Secret environment variables: passwords, tokens, API keys. They work like
[env](#env), except their keys and values never leave the daemon. To read from a
file, use [secrets_file](#secrets_file).

```toml
[tasks.backup.secrets]
RESTIC_PASSWORD = "${file:~/.config/runwisp/restic.pass}"
```

### env_file

**type**: `string`

Path to a dotenv file merged beneath [env](#env) (inline entries win). Its values
are visible in the API/UI, like `env`. Paths may be absolute, `~/`-relative, or
relative to the `runwisp.toml` directory. Plain `KEY=VALUE` lines, read literally
with no shell expansion.

```toml
[tasks.backup]
env_file = "backup.env"
```

### secrets_file

**type**: `string`

Path to a dotenv file merged beneath [secrets](#secrets). Only the path is ever
visible in the API/UI, never the contents. Same path resolution and format as
[env_file](#env_file).

```toml
[tasks.backup]
secrets_file = "/etc/runwisp/backup-secrets.env"
```

## Parameters

### params

**type**: `table` (array of `[[tasks.<name>.params]]` entries)

Declare the inputs a task takes. Each one becomes a field on the Web UI, TUI, and
REST Run Task form, so an operator can fill it in per run. Every entry sets exactly
one identity keyword (`env`/`arg`/`option`/`flag`), which decides how the value
reaches your command. Values always arrive as real argv entries or env vars, never
spliced into the shell string, so an operator typing `; rm -rf /` gets an inert
string. Scheduled runs (cron, catch-up, retries) use the declared defaults.

```toml
[tasks.backup]
run = "/usr/local/bin/backup.sh"
params = [
  { env = "PROJECT_ID", required = true },
  { arg = "source", required = true },
  { arg = "dest", default = "/backups" },
  { option = "--region", choices = ["us", "eu"] },
  { flag = "--force" },
]
```

Identity keyword (exactly one per entry):

- `env`: expose the value as an environment variable of that name. Can't collide
  with a static `env`/`secrets` key on the same task.
- `arg`: append the value as a positional argument, in declaration order.
- `option`: render as `--name value`. A name ending in `=` glues them
  (`--date=2026-01-01`).
- `flag`: a boolean whose token is appended when on, omitted when off. Takes no
  `choices` or `type`.

Attributes:

- `default`: value scheduled runs use and manual forms pre-fill (`true`/`false` for
  a flag). A parameter with a `default` is safe on a scheduled task.
- `required`: the manual form won't submit without a value (`env`/`arg`/`option`). A
  required parameter on a scheduled task must also set `default`.
- `type`: `string` (default) or `number`; a `number` that doesn't parse is rejected
  before the run starts.
- `choices`: restrict to a fixed list, shown as a dropdown. Values outside it are
  rejected.
- `allow_custom`: with `choices`, also let the operator type a value not in the
  list. Meaningless (and rejected) without `choices`.
- `description`: help text shown under the field.

:::note[Omitting a value vs. passing an empty one]
When you trigger a task by hand, clearing a field and passing an empty string differ.

- Leave a field as-is and its value (the default, or what you typed) is passed.
- Clear it and the parameter is omitted: the option, arg, or env var isn't passed at
  all. Clearing does not fall back to the default; a `required` field can't be
  omitted.
- Pass an empty string when your program distinguishes `--note ''` from no `--note`:
  use the toggle under the field (in the TUI, ctrl+t).

Flags have no ambiguity: off means the token isn't appended. Scheduled runs and
retries use the declared defaults, and a retry replays exactly what the original run
was given.
:::

## Working directory & shell

### working_dir

**type**: `string`

The directory the process runs in. Relative paths resolve against the `runwisp.toml`
directory, and `~` is the home of whoever the task runs as. Existence is checked at
run time, not load. Unset, the run inherits the daemon's directory.

```toml
[tasks.build]
working_dir = "/srv/app"
run         = "./bin/build"
```

### shell

**type**: `string` **default**: `/bin/sh`

The interpreter for `run`, as an absolute path. Set `/bin/bash` for arrays,
`[[ ]]`, or `set -o pipefail`. It's invoked as `<shell> -e -c <script>`, so
fail-fast is armed for POSIX shells (RunWisp warns at boot when it can't arm it).
Can be set once in `[defaults]`.

```toml
[tasks.report]
shell = "/bin/bash"
run   = "set -o pipefail; make report | tee out.log"
```

### umask

**type**: `string`

The octal file-creation mask applied to the run: `"027"` makes new files
`rw-r-----`. Write at least three digits (`"022"`, not `"22"`). Applied inside the
run's own process, so concurrent runs never affect each other. Empty inherits the
daemon's umask.

```toml
[tasks.dump]
umask = "027"
```

### env_base

**type**: `enum` **default**: `"inherit"`

What the run's environment starts from, before `env`/`secrets` layer on top. Host
shell only: it's an error on a compose-backed task.

```toml
[tasks.legacy-nightly]
env_base = "clean"
run      = "/usr/local/bin/nightly"
```

Possible values:

- `inherit`: start from the daemon's own environment. The run then depends on how
  the daemon was launched.
- `clean`: start from just `PATH`, `SHELL`, `HOME`, and `USER`/`LOGNAME` (what cron
  gives a job), so runs stay reproducible. Declare the rest in [env](#env).

### user

**type**: `string`

Drop the run to another OS account, as `user` or `user:group` (name or numeric id,
the shorthand `chown` and Compose use). RunWisp resolves the account at start,
seeds `HOME`/`USER`/`LOGNAME`, and applies its groups. Works only when the daemon
runs as root; otherwise the run fails loudly. Empty keeps the daemon's identity.

```toml
[tasks.report]
user = "reporter:reporter"
```

## Compose-backed tasks

### compose_file

**type**: `string`

Point the task at a docker-compose file so a firing runs a compose service instead
of a plain `run`. With only `compose_file` set, each firing does
`docker compose run --rm <svc>` with the service's own command. Pair it with `run`
and `compose_mode = "exec"` to run your command inside the running container.

```toml
[tasks.nightly-backup]
cron            = "0 3 * * *"
compose_file    = "./docker-compose.yml"
compose_service = "backup"
```

### compose_service

**type**: `string` **default**: the task name

Which service inside the [compose_file](#compose_file) to run. Requires
`compose_file`.

```toml
[tasks.nightly-backup]
compose_file    = "./docker-compose.yml"
compose_service = "backup"
```

### compose_mode

**type**: `enum` **default**: `"exec"` when `run` is set, else `"run"`

How a [compose_file](#compose_file)-backed unit runs.

```toml
[tasks.migrate]
compose_file = "./docker-compose.yml"
compose_mode = "exec"
run          = "rails db:migrate"
```

Possible values:

- `run`: start a fresh container each firing (`docker compose run --rm`)
- `exec`: run your command inside the running container (`docker compose exec`)

## Notifications

### notify

**type**: `string[]`

Notifier ids to page whenever a run ends in something [failures](#failures)
classifies as a failure. Entries are ids from your `[notifiers.<id>]` blocks (or
`inapp`), optionally `"id:override"` to retarget a channel. Whatever is in
`[notify] global_notifiers` (default `["inapp"]`) is added automatically. To alert
on a non-failure outcome, add an explicit `[[route]]` matching that kind.

```toml
[tasks.deploy]
notify = ["slack-ops"]
```

## Constraints

:::caution[What's rejected on tasks]
The config loader turns these away at startup, so they can't quietly bite you later.

- `restart` / `restart_attempts`: services-only. A task re-runs a failed run with
  [retry_attempts](#retry_attempts) / [retry_delay](#retry_delay) /
  [retry_backoff](#retry_backoff), not restart.
- `instances`, `priority`, `autostart`, `depends_on`: services-only fields.
- A task name also taken by a `[services.*]`: they share one namespace.
- An empty or missing `run` (unless [compose_file](#compose_file) is set).
  :::

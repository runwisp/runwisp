`[daemon]` carries the small set of settings that apply to the daemon
as a whole rather than to any individual task or service. It is optional;
omit the section and the built-in defaults below take over.

The **data directory** and **listen address** are deliberately not in
TOML — they need to be settable before the config file is even read, so
they live on the CLI (or in your supervisor's invocation of `runwisp`).
They're documented here alongside the in-TOML keys because operators
think of them together.

## Keys

```toml
[daemon]
shutdown_timeout     = "10s"
allow_cloud_dispatch = false
```

| Key                    | Default | What it does                                                                                                                                                              |
| ---------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shutdown_timeout`     | `"10s"` | Whole-daemon shutdown budget. After `SIGTERM`, the daemon SIGKILLs any in-flight runs that haven't exited within this window so the process can actually exit.            |
| `allow_cloud_dispatch` | `false` | Opt-in flag for ad-hoc task execution requested by a connected control-plane peer. Off by default — the daemon never accepts peer-dispatched shell unless this is `true`. |

### `shutdown_timeout`

`shutdown_timeout` is the **whole-daemon** budget. Each task and service
still gets its own [`graceful_stop`](/configuration/tasks/#retries--timeout)
inside that cap. If any `graceful_stop` exceeds `shutdown_timeout` the
daemon emits a boot-time warning naming the offending task — the daemon
will SIGKILL the survivor before its per-task grace window completes.

Either raise `shutdown_timeout`, lower the per-task `graceful_stop`, or
accept that the task's cleanup hook may be interrupted on daemon
shutdown.

### `allow_cloud_dispatch`

Set this to `true` only if you've connected the daemon to a
control-plane peer and want that peer to be able to fire ad-hoc shell
runs that aren't declared in `runwisp.toml`. Ad-hoc runs are logged
and persisted like any normal run; they just bypass the TOML task set.

Even with `allow_cloud_dispatch = true`, the daemon never executes
strings from regular REST or Web UI traffic — only authenticated
control-plane messages over the WebSocket protocol can dispatch them.

## CLI flags: data directory & listen address

These three flags govern where state lives and where the HTTP/Web UI
listens. They apply to every `runwisp` subcommand (`daemon`, `tui`,
`exec`, …):

| Flag     | Default     | What it does                                                                               |
| -------- | ----------- | ------------------------------------------------------------------------------------------ |
| `--data` | `data`      | Directory for all persistent state — SQLite database, per-task logs, JWT secret, PID file. |
| `--host` | `127.0.0.1` | Bind address for the HTTP server. Use `0.0.0.0` to listen on every interface.              |
| `--port` | `9477`      | TCP port for the HTTP server (REST API, SSE log stream, Web UI).                           |

```sh
runwisp daemon --data /var/lib/runwisp --host 0.0.0.0 --port 9477
```

Picking `--data` once and using it consistently matters: the database
file (`runwisp.db`), the JWT secret, and every task's log files all
live under that directory. Moving it after the fact is a directory
move, not a configuration change.

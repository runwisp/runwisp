Point [`include_cron`](/configuration/daemon/#include_cron) at `/etc/crontab`
while cron is still running and you'd expect an obvious problem: two schedulers,
one job, two backups a night.

That doesn't happen. While a system cron daemon is alive, RunWisp **holds** every
job it read from cron's own files — it loads them, lists them, shows their
schedules, and does not fire them, because cron already is. So you can turn
`include_cron` on today and retire cron whenever you're ready.

## What a hold stops

A held job isn't a warning label on something that's still scheduled. RunWisp
never puts it on its own scheduler at all, so there's nothing on RunWisp's side
to collide with cron. A held task gets no cron firing, no startup jitter, no
`run_on_start` (so an imported `@reboot` job stays cron's), no catch-up runs,
and no missed-tick detection.

That last one is why handing the jobs over doesn't arrive with a backlog of
alerts for ticks cron ran perfectly well: nothing is recorded during the hold, so
there's no gap to reconcile.

What you can still do is run a held job on demand — `runwisp exec <name>`, the
API trigger, or `r` in the TUI. That's the point of the window: you can watch a
job run under RunWisp, captured output and all, before you commit.

What you don't get is history or output for the scheduled firings. Cron is
running those, so there's nothing for RunWisp to capture — which is the reason to
finish the handover rather than leave it half-done.

## When a job is held

Three things have to be true, and the last one is per file:

1. **A live system cron daemon is detected.** A `cron.service`, `crond.service`,
   or `cronie.service` that `systemctl` reports as active — or merely as
   _enabled_, since it's back on the next boot. On a box with no `systemctl`,
   RunWisp falls back to cron's pidfiles and checks the process named inside is
   actually alive.
2. **The job came from `include_cron`**, not from your own TOML and not from a
   [staged import](/replacing-cron/converting-crontabs/).
3. **Its source file is one cron reads itself** — `/etc/crontab`, any path with a
   `cron.d` component, or a file sitting directly in a per-user spool directory.
   The [`include_cron` path table](/configuration/daemon/#which-files-and-who-the-jobs-run-as)
   lists exactly which paths qualify.

There's no `held` key in TOML. It isn't stored, either — RunWisp re-derives it by
asking the box afresh, so there's never stale hold state to clear.

## Where you see a hold

A hold is never silent. Every surface reports it:

| Where                         | What you see                                                                                                |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Boot                          | A `HELD:` banner on stderr, naming the tasks and the command that ends the hold.                            |
| `runwisp status`              | A `⏸` block listing the held tasks.                                                                         |
| `runwisp validate`            | The same block, naming the cron daemon it found. Not a warning — the exit code is unchanged.                |
| `runwisp list`                | Nothing. The human table has no held column — use `--json`.                                                 |
| `runwisp list --json`         | `"held_by": "cron"` on each held task.                                                                      |
| `runwisp status --json`       | The same field, per task.                                                                                   |
| `GET /api/tasks`, `/api/info` | The same field. `/api/info` is rebuilt per request, so a released hold is never reported stale.             |
| TUI                           | A header chip reading `⏸ N held by cron`, and a `⏸ held` line on the task with its `Next:` time suppressed. |
| Web UI                        | A `held` badge on the task, with the full explanation in its tooltip.                                       |

At boot the banner looks like this:

```
================================================================================
  HELD: 12 tasks are not being scheduled by RunWisp.
  A system cron daemon is running and still owns the crontabs they came from.
  RunWisp is standing down so nothing fires twice — cron keeps running these
  jobs, and RunWisp records no history or output for them.
    backup, healthcheck, logrotate, warmup
  Run 'sudo runwisp takeover' to hand them over. Or just stop cron: RunWisp
  notices within a minute and takes them on, no reload needed.
================================================================================
```

`held_by` is a string, not a boolean, and it's absent when a task isn't held — so
test for its presence rather than expecting `"held_by": ""`. Its only value today
is `"cron"`.

## The hold ends on its own

You don't have to tell RunWisp when cron is gone. The daemon re-checks whether a
cron daemon is alive about once a minute, so the jobs become RunWisp's within a
minute of cron going away — however you did it:

```bash
sudo runwisp takeover              # writes config, masks cron, hands over at once
sudo systemctl disable --now cron  # or do it yourself; RunWisp catches up
```

[`runwisp takeover`](/replacing-cron/take-over-from-cron/) is instant rather than
"within a minute" because it reloads the running daemon as its last step. Either
way, **no reload is required** — reloading after you retire cron only makes the
handover immediate.

It works in reverse too. If cron comes back — an operator, a package upgrade —
RunWisp re-holds those jobs before the next tick can fire twice, and logs that
it's standing down again.

## The one file that isn't held

A crontab-format file in a path cron never looks at, say `/opt/myapp/jobs.cron`,
is not held. Cron isn't reading it, so those jobs are yours alone and RunWisp
schedules them normally.

If something _else_ reads that file too, RunWisp can't tell. So when cron is live
and you're reading a file outside cron's own paths, you get a warning saying
exactly that, and the job stays scheduled. It's the one case where the call is
yours.

## An imported copy is never held

A hold needs RunWisp to know a job is the same job cron is running, and that link
only exists for a file read live through `include_cron`.
[`runwisp import cron`](/replacing-cron/converting-crontabs/) **copies**
definitions instead, and a copy has no link back to the crontab line it came
from — so RunWisp can't recognise it and can't hold it.

:::caution[An import means you retire the cron line yourself]
Convert a job to TOML and leave it enabled in cron, and both schedulers fire it.
Nothing errors. See
[Retiring the crontab](/replacing-cron/converting-crontabs/#retiring-the-crontab)
for the commands.
:::

There are two ways to bring cron jobs into RunWisp, and you don't have to
hand-translate anything either way:

- **Point RunWisp at your crontabs and leave them there.** One line of config,
  no conversion, nothing rewritten — and while cron is alive the jobs are
  [held](/replacing-cron/held-jobs/) rather than fired, so nothing runs twice.
  Best if you want visibility today and will tidy up later. Start with
  [Take over from cron](/replacing-cron/take-over-from-cron/).
- **Convert to TOML with `runwisp import cron`.** You end up with a config you
  own, annotated with anything that needed a human's attention. Best if you want
  the crontab gone. That's this page.

The important difference: an import **copies**. The copy has no link back to the
crontab line it came from, so RunWisp can't tell it's the same job and can't hold
it. Converting means you're taking on retiring the cron line yourself — see
[Retiring the crontab](#retiring-the-crontab) at the end.

## The one-liner

Pipe your current crontab in, or point it at a file — both work the same way:

```bash
crontab -l | runwisp import cron        # whatever's installed for you
runwisp import cron /etc/crontab        # a specific file
```

That prints an annotated `runwisp.toml` to your terminal and a summary of what
it did. Given a crontab like:

```text
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin
MAILTO=ops@example.com

# Nightly database backup
30 2 * * * /usr/local/bin/backup.sh --full
@reboot /opt/app/warmup
*/5 * * * * /opt/healthcheck.sh
```

you get:

```toml
#:schema https://docs.runwisp.com/config.schema.json
# Generated by `runwisp import`. Review the notes below, then
# validate with `runwisp validate`.

[tasks.backup]
description = "Nightly database backup"
cron = "30 2 * * *"
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
catch_up = "skip"  # cron never re-fires a missed tick
on_overlap = "queue"  # cron would overlap instead of queueing
run = "/usr/local/bin/backup.sh --full"

[tasks.backup.env]
PATH = "/usr/local/bin:/usr/bin"

# @reboot — runs once each time the daemon starts.
[tasks.warmup]
run_on_start = true
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
on_overlap = "queue"  # cron would overlap instead of queueing
run = "/opt/app/warmup"

[tasks.warmup.env]
PATH = "/usr/local/bin:/usr/bin"

[tasks.healthcheck]
cron = "*/5 * * * *"
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
catch_up = "skip"  # cron never re-fires a missed tick
on_overlap = "queue"  # cron would overlap instead of queueing
run = "/opt/healthcheck.sh"

[tasks.healthcheck.env]
PATH = "/usr/local/bin:/usr/bin"
```

Every task carries the crontab's `SHELL` and `PATH` itself, rather than a shared
`[defaults]` block — more verbose, but each task stands alone and your own global
settings are left untouched. The `env_base`, `working_dir`, `catch_up` and
`on_overlap` lines reproduce cron's execution model rather than the daemon's —
see [How cron maps to TOML](/replacing-cron/cron-mapping/). (`warmup` gets no
`catch_up`: a `@reboot` job has no ticks to miss.)

On stderr — so it stays out of the TOML you're piping somewhere — you get an
account of every job:

```
Imported crontab → 3 tasks
  ✓ backup        30 2 * * *
      /usr/local/bin/backup.sh --full
  ✓ warmup        @reboot
      /opt/app/warmup
  ✓ healthcheck   */5 * * * *
      /opt/healthcheck.sh

Notes:
  ! crontab sets MAILTO=ops@example.com. crond mails a job's output; RunWisp
    notifies on the event instead, so the closest equivalent is a sendmail
    notifier through the same MTA. Add to your root runwisp.toml:
        [[notifier]]
        id   = "mta"
        type = "sendmail"
        from = "runwisp@localhost"
        to   = ["ops@example.com"]
    then put notify_on_failure = ["mta"] on the tasks you want mail from. Note
    the difference: crond mailed any output at all, this mails failures.

Review the TOML above, save it as runwisp.toml, then run `runwisp validate`.

! cron still runs these jobs. Comment them out (`crontab -e`, or move the
  file out of /etc/cron.d) before starting RunWisp, or each one runs twice.
```

That last `!` is specific to importing. It's there because a copy can't be held
— if you'd pointed `include_cron` at the same file instead, RunWisp would have
held those jobs and the warning wouldn't apply.

Every line of your crontab gets a row, and the row shows the command that will
actually run — wrapped if it's long, never cut short, because a `2>&1` you can't
see is a `2>&1` you can't check. The mark tells you how it landed:

| Mark | Means                                                    |
| ---- | -------------------------------------------------------- |
| `✓`  | Mapped cleanly.                                          |
| `~`  | Imported, but something changed — the row says what.     |
| `!`  | Needs a fix from you before this config will load.       |
| `-`  | Skipped, because your `runwisp.toml` already defines it. |

Anything about the file rather than about one job — a `MAILTO`, an unresolvable
`[include]` — lands in `Notes:` at the bottom. Nothing is dropped without a line.

When it looks right, save it:

```bash
crontab -l | runwisp import cron -o runwisp.toml
runwisp validate
```

`-o` writes the file (it won't clobber an existing `runwisp.toml` without
`--force`), and [`runwisp validate`](/configuration/overview/) confirms the
result parses before you start the daemon.

## Keeping your own config separate

`-o` gives you one flat file, which is perfect when you're starting fresh. If
you already have a `runwisp.toml` you've been hand-writing, use `--write`
instead:

```bash
crontab -l | runwisp import cron --write --dry-run   # look first
crontab -l | runwisp import cron --write             # then do it
```

`--dry-run` prints the same summary and names every file the real run would
touch, without touching any of them:

```
Would stage 3 tasks in /etc/runwisp/runwisp.d/imported.toml
Would create /etc/runwisp/runwisp.toml and wire it to load runwisp.d/*.toml.

Not checked: whether these merge with the tasks you already have.
A real run checks that, and rolls both files back if it fails.

! cron still runs these jobs. Comment them out (`crontab -e`, or move the
  file out of /etc/cron.d) before starting RunWisp, or each one runs twice.

Nothing was written.
```

The real thing installs the import in a **two-tier layout**:

```
runwisp.toml              # yours — hand-authored, keep it in git
runwisp.d/imported.toml   # machine-owned — the importer writes this
```

Your root file is created (or has its
[`[daemon].include`](/configuration/daemon/) wired) to load `runwisp.d/*.toml`,
and the imported jobs land in the staging file. Nothing you wrote by hand is
touched — the importer only ever owns `runwisp.d/imported.toml`, so you can
re-run the import without worrying about what it'll do to your own tasks.

A name that clashes with a task you already have doesn't break anything either.
If your `runwisp.toml` already defines that name with the **same** command, the
job is skipped as already-yours (a `-` row). If it defines it with a _different_
command, the imported one is renamed — `backup` becomes `backup-2` — and the row
says so, so you never end up with a config that won't load and never silently
lose a job. Both files are still written as one unit, so a merge that fails for
any other reason rolls both back rather than leaving your daemon half-updated.

Imported tasks report `"source": "staged"` in `runwisp list` and `status --json`
— shorthand for "came from an import, not native TOML yet". It's a label, not a
limitation: staged tasks are scheduled and run exactly like any other.

:::note
If your root config already sets its own `include` list, `--write` won't edit it
behind your back. It prints the glob to add and writes nothing.
:::

## Graduating a job into your own config

Staging is a waiting room. When you're happy with an imported job, promote it:

```bash
runwisp promote backup      # move this one into runwisp.toml
runwisp promote --all       # move all of them
```

That moves the job's block out of `runwisp.d/imported.toml` and into your own
`runwisp.toml`, comments and all — including any `# TODO` the import left for
you. Nothing is re-generated, so nothing gets reformatted or lost on the way.
From then on the job is yours: it reports no `source` any more, and a later
re-import won't touch it.

Nothing about the job's behaviour changes — only which file defines it. A
promoted service keeps running, and `runwisp reload` afterwards will honestly
report _no task changes_; the reload is just there to refresh the provenance
label on a live daemon. Use `--reload` to do both in one go, or `--dry-run`
first if you want to see exactly which bytes would move.

Convert one job a week or all of them at once — RunWisp doesn't mind. When the
last one is promoted the empty staging file is cleaned up, and you're left with
a single hand-maintained `runwisp.toml`, exactly as if you'd written it
yourself.

`promote` works on a crontab-sourced task too, not just an imported one: it
copies the definition into your `runwisp.toml` while leaving the crontab
untouched. On the next load RunWisp notices your TOML says the same thing the
crontab does and takes the TOML copy, so you can delete the cron line whenever
you feel like it.

## Retiring the crontab

An import copies your jobs; it never touches your crontab. And because a copy
[can't be held](/replacing-cron/held-jobs/), starting the daemon with cron still
enabled means every imported job has two schedulers firing it — two backups a
night. So take the imported jobs away from cron by hand:

```bash
crontab -l > ~/crontab.backup    # keep a copy, always
crontab -e                       # comment out the lines you imported
```

For a system crontab, move the file instead of editing it — cron picks up
`/etc/cron.d` by directory listing:

```bash
sudo mv /etc/cron.d/myjobs /root/myjobs.crontab.backup
```

To go all-in, `crontab -r` drops your user crontab entirely. Take the backup
first — it's unrecoverable, the one command on this page you can't undo.

If you'd rather cut over gradually, that works too: comment out one job, let
RunWisp own it for a few days, then do the next. Just don't leave a job enabled
in both places — pick one owner per job and the schedules stay honest.

:::tip[Or skip all of this]
If you point [`include_cron`](/configuration/daemon/#include_cron) at the
crontabs instead of importing them, none of this is yours to manage:
`sudo runwisp takeover` retires cron in one step, and nothing can double-fire
in the meantime. See [Take over from cron](/replacing-cron/take-over-from-cron/).
:::

## System crontabs and the user column

`/etc/crontab` and files in `/etc/cron.d` put a **user** between the schedule
and the command. RunWisp spots those automatically — from the path, or from the
`# m h dom mon dow user command` header — and maps that column to the task's
[`user`](/configuration/tasks/). You don't have to flag it.

If a piped crontab is ambiguous, the importer leaves a `# TODO` at the top of
the file rather than guessing wrong. Force the decision either way with
`--system` or `--system=false`:

```bash
runwisp import cron /etc/crontab -o runwisp.toml   # auto-detected
crontab -l | runwisp import cron --system=false    # never treat a column as a user
```

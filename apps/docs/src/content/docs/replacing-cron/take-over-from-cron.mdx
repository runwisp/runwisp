Cron runs your jobs but tells you nothing — a job fails at 3am and you find out
from the missing file the next morning. `runwisp takeover` hands those jobs to
RunWisp without touching your crontabs: same schedules, but now with history,
captured output, and notifications.

```bash
sudo runwisp takeover
```

:::caution[Linux with systemd, as root]
Retiring cron means _masking_ it — telling systemd to refuse to start
`cron.service` so it can't come back on boot or by hand. That needs `systemctl`
and `sudo`, and it's fully reversible. It isn't possible on macOS — see
[macOS](#macos) for the manual route.
:::

## What it does

RunWisp reads your existing crontabs in place. Nothing is converted or rewritten,
and `crontab -e` keeps working. While cron is still alive, RunWisp
[holds](/replacing-cron/held-jobs/) those jobs instead of firing them, so nothing
runs twice during the handover.

`takeover` runs these steps, in order:

1. **Write the config** — a `runwisp.toml` that reads your crontabs via
   [`include_cron`](/configuration/daemon/#include_cron), or that key added to a
   config you already have. Comments, key order, and formatting are left alone.
2. **Install the service** — `/etc/systemd/system/runwisp.service` with your
   binary, config, data dir, port, and host, then `systemctl daemon-reload`.
3. **Stop and mask cron** — stop it, then mask it so systemd won't start it again.
   Stop comes first, so cron can't fire in the gap.
4. **Start RunWisp** — `systemctl enable --now runwisp.service`.

Cron isn't touched until RunWisp's config and unit are both on disk. If step 4
fails, RunWisp unmasks cron (and restarts it if it was running) rather than leave
the box with no scheduler, then shows you the original error.

## The prompt

You don't need a `runwisp.toml` first. On a box with cron jobs, `takeover` finds
the crontabs, shows the full plan, and asks once:

```
Found 12 cron jobs on this box:
  /etc/crontab, /etc/cron.d

 1. Write /etc/runwisp/runwisp.toml
       reads /etc/crontab, /etc/cron.d live via [daemon] include_cron
 2. Install RunWisp as a system service and retire cron.service
       write /etc/systemd/system/runwisp.service
       systemctl daemon-reload
       stop cron.service
       mask cron.service
       systemctl enable --now runwisp.service

Resolved settings:
  Binary:    /usr/local/bin/runwisp
  Config:    /etc/runwisp/runwisp.toml
  Data dir:  /var/lib/runwisp
  Host:      127.0.0.1
  Port:      9477

Take over from cron.service? [Y/n]
```

Nothing is written until you answer yes. If you already have a `runwisp.toml`,
step 1 becomes "Add `include_cron` to it"; if it already reads the crontabs, step
1 is marked done and skipped.

If RunWisp was already running, a reload is added as a final step — that's what
makes the handover instant instead of "within a minute".

Re-running a finished take-over is a no-op: every step comes back done, exit 0.
For a scriptable check without a terminal, use [`--dry-run`](#flags).

## First-run shortcut

On a fresh root box with a live cron unit and no `runwisp.toml`, plain `runwisp`
offers the same cutover from one prompt:

```
No runwisp.toml at /etc/runwisp.
Found 12 cron job(s) on this box (/etc/crontab, /etc/cron.d).

RunWisp can take over from cron. It will:
  · read /etc/crontab and /etc/cron.d as RunWisp tasks (crontab -e still works)
  · install itself as a system service, so it starts on boot
  · stop and mask cron.service, so nothing fires twice

Take over from cron? [Y/n]
```

You see this only when everything lines up: readable crontabs with jobs, Linux as
root, an interactive terminal, an **active** cron systemd unit, and nothing on the
[blocked list](#when-it-refuses). Otherwise RunWisp still offers to read the
crontabs and notes that `sudo runwisp takeover` finishes the job later.

Saying yes writes the config first, so declining the install afterwards leaves you
with the config and cron untouched. This never happens non-interactively —
`runwisp daemon`, systemd, and Docker never mask cron behind your back.

## `service install` doesn't retire cron

`sudo runwisp service install` only wires up the unit. If cron is still running
jobs, it says so and names the command that fixes it:

```
Note: cron.service is still running, and owns 12 cron job(s) on this box.
      Run 'sudo runwisp takeover' to hand them to RunWisp.
```

## When it refuses

Anything RunWisp can fix itself becomes a step, not a refusal. What's left is
reported all at once, before anything is written:

| Blocker                                           | What to do                                                                                                                               |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Not Linux with systemd                            | See [macOS](#macos) for the manual route.                                                                                                |
| Not root                                          | Re-run with `sudo`. A user-scoped daemon can't run another account's jobs.                                                               |
| No cron jobs found                                | Point [`include_cron`](/configuration/daemon/#include_cron) at them if they live somewhere unusual. RunWisp names the paths it searched. |
| `runwisp.toml` won't load                         | Fix the config. Nothing is written and cron is untouched.                                                                                |
| `runwisp.toml` isn't trusted for a system install | Run the `chown`/`chmod` RunWisp prints — the unit runs as root.                                                                          |
| Your `include_cron` misses some crontabs          | Paste the array RunWisp prints. Not overridable — masking cron while a crontab goes unread would silently stop that job.                 |
| A cron source failed to load                      | Fix it, or pass `--allow-skipped-cron-jobs` to take over anyway; those jobs stay stopped.                                                |

If you maintain `include_cron` yourself, RunWisp won't edit it — it names the
files that would go unread and prints the exact array to paste.
`--allow-skipped-cron-jobs` is the only blocker you can wave through.

Jobs stay held while you sort any of this out, so nothing fires twice meanwhile.

## Undoing it

`runwisp service uninstall` reverses the take-over — it unmasks the cron unit and
starts it again. It only does that when this instance's own unit recorded the
take-over (a `# runwisp-masked-cron: <unit>` marker). RunWisp never unmasks a
service it can't prove it masked.

`runwisp service status` shows a `Cron:` row once that marker exists:

```
  Cron:       cron.service masked by this instance
```

Two other values are possible, both degraded:

```
  Cron:       cron.service active — jobs may be firing twice
  Cron:       cron.service unmasked but not running (unexpected — check by hand)
```

The first means something brought cron back. Jobs RunWisp reads straight from
cron's files are safe — the daemon spots the live cron within a minute and
[stands down again](/replacing-cron/held-jobs/#the-hold-ends-on-its-own). Anything
you'd converted to TOML has no such protection and really is running twice. Either
way, re-run `sudo runwisp takeover` — the plan shows the config and unit already
done, with only the cron half left:

```
 ✓ /etc/runwisp/runwisp.toml already reads /etc/crontab, /etc/cron.d
 1. Install RunWisp as a system service and retire cron.service
       stop cron.service
       mask cron.service

Take over from cron.service? [Y/n]
```

The second means cron is unmasked but nothing started it. Look before something
does.

## Flags

| Flag                        | What it does                                                                                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--dry-run`                 | Print the plan and exit — no prompt, no writes. Exits non-zero if the take-over is blocked, so a provisioning script can check it without a terminal. |
| `--yes`, `-y`               | Take over without asking (for provisioning scripts).                                                                                                  |
| `--force`                   | Overwrite a hand-edited unit. Does _not_ skip the confirmation.                                                                                       |
| `--allow-skipped-cron-jobs` | Take over even though some cron jobs failed to load.                                                                                                  |
| `--binary`                  | Override the binary path baked into the unit (default: detected).                                                                                     |

The global `--config`, `--data`, `--port`, and `--host` set the values baked into
the unit; left alone they resolve to root's defaults (`/etc/runwisp/runwisp.toml`,
`/var/lib/runwisp`). See the full set in the
[CLI reference](/operations/cli/#retire-cron).

## macOS

macOS's cron (`com.vix.cron`) lives under SIP-protected
`/System/Library/LaunchDaemons`, which nothing running as your user can mask, and
RunWisp has no system-wide install on macOS to mask it from. `runwisp takeover`
refuses and points you at the manual route: convert the jobs with
[`runwisp import cron --write`](/replacing-cron/converting-crontabs/), watch them
run under RunWisp, then remove the crontab yourself (`crontab -r`).

There's no hold to cover you meanwhile — detecting a live cron needs `systemctl`
or a Linux pidfile, and macOS has neither. Retire each crontab line by hand as you
go.

## What it doesn't do

- **Never rewrites your crontabs.** They stay as they are; RunWisp re-reads them
  on [reload](/operations/reload/).
- **Never converts anything.** For TOML you own, use
  [`runwisp import cron`](/replacing-cron/converting-crontabs/).
- **Doesn't remove cron.** Masking is reversible with `service uninstall`.
- **Doesn't touch your task definitions.** The only config change is `include_cron`.

## The other route

Instead of reading crontabs in place, you can convert them to TOML you own with
`runwisp import cron`. That copies the jobs, and a copy
[can't be held](/replacing-cron/held-jobs/#an-imported-copy-is-never-held) — so
prefer `takeover` if you want the guarantee against double-firing during the
switch. Convert when you want the crontab gone.

There are two ways to move cron jobs to RunWisp:

- **Take over** (Linux with systemd): RunWisp reads your crontabs where they
  are and replaces the cron service. `crontab -e` keeps working; run
  `sudo runwisp reload` after an edit. Until you do, `runwisp status`,
  `runwisp list`, the TUI and the notification bell name the crontab that
  changed.
- **Convert by hand** (any system): `runwisp import cron` turns a crontab into
  TOML, and you disable the old cron lines yourself.

Either way, you can later [promote](#staging-and-promoting) any job into your
own `runwisp.toml`.

## Take over in one command

```bash
runwisp takeover
```

You don't need a `runwisp.toml` first. `takeover` finds your crontabs, shows a
plan that lists each job with the task it becomes, and asks once. Nothing is
written until you say yes.

:::caution[Linux with systemd, as root]
`takeover` retires cron by masking its systemd unit, so systemd won't start it
again. This needs root and systemd. Run it as yourself and it re-runs itself
with sudo. In a container, see [In a container](#in-a-container). On macOS or
without systemd, [convert by hand](#convert-by-hand).
:::

### What it does

1. **Writes the config**: a `runwisp.toml` that reads your crontabs and
   `/etc/anacrontab` with [`include_cron`](/configuration/daemon/#include_cron).
   In an existing config it adds the key and leaves comments and formatting
   alone. An `include_cron` you wrote is never edited: if it misses a crontab,
   the take-over stops and prints the list to paste. The one RunWisp wrote
   itself gets any source a newer RunWisp reads, such as `/etc/anacrontab`.
2. **Installs the service**: `/etc/systemd/system/runwisp.service`, then
   `systemctl daemon-reload`. If the binary you ran isn't owned by root, it is
   [copied to `/usr/local/bin`](/operations/autostart/) first.
3. **Stops and masks cron**: stopped first, so nothing runs in between. If
   anacron is installed (it runs `cron.daily`, `cron.weekly` and `cron.monthly`
   on Debian, Ubuntu and Fedora), `anacron.timer` and `anacron.service` are
   stopped and masked with it.
4. **Starts RunWisp**: `systemctl enable --now runwisp.service`. `@reboot`
   lines don't run now, because cron already ran them when the machine booted.
   They run again on the next boot.

When it's done, it prints the dashboard address, and the commands for the
password (`sudo runwisp password`) and for upgrades (`sudo runwisp upgrade`).
Over SSH it also prints the `ssh -L` command that tunnels the dashboard to your
own machine.

Cron isn't touched until the config and unit are on disk. If RunWisp fails to
start, cron is unmasked (and restarted if it was running), and you see the
error.

Distro lines that do nothing on this machine, such as
`test -x /usr/sbin/anacron || run-parts …`, are listed as left out instead of
imported. See [`include_cron`](/configuration/daemon/#include_cron).

If a crontab sets `MAILTO`, the plan warns that cron mail stops. Set up
[notifications](/notifications/) to hear about failures; see
[`MAILTO`](#what-needs-a-human) below.

The plan also counts jobs that redirect their output. A trailing
`>/dev/null 2>&1` is dropped (see [below](#how-cron-maps-to-runwisp)). A job
that still writes to a file (`>> /var/log/sync.log 2>&1`) shows no output in
RunWisp. To see it there, remove the redirect from the crontab line, then run
`sudo runwisp reload`.

Your crontabs are never rewritten. Running `takeover` again on a finished
take-over does nothing and exits 0. Flags such as `--dry-run` and `--yes` are
in the [CLI reference](/reference/cli/#runwisp-takeover).

### The prompt

```
Found 12 cron jobs on this box:
  /etc/crontab, /etc/cron.d

 1. Write /etc/runwisp/runwisp.toml
       reads /etc/crontab, /etc/cron.d live via [daemon] include_cron
 2. Install RunWisp as a system service and retire cron.service
       write /etc/systemd/system/runwisp.service
       systemctl daemon-reload
       stop cron.service
       mask cron.service
       systemctl enable --now runwisp.service

Resolved settings:
  Binary:    /usr/local/bin/runwisp
  Config:    /etc/runwisp/runwisp.toml
  Data dir:  /var/lib/runwisp
  Host:      127.0.0.1
  Port:      9477

Take over from cron.service? [Y/n]
```

On a root box with cron jobs, running plain `runwisp` the first time offers the
same take-over. Only a command you run in a terminal ever masks cron;
`runwisp daemon`, systemd, and Docker never do.

### Held jobs

While cron is still running, RunWisp **holds** the jobs it reads from cron's
files: they are listed with their schedule, but RunWisp doesn't start them, so
nothing runs twice. At boot, a `HELD:` banner names them.

- Held tasks show `⏸` in `runwisp status` and the TUI, a `held` badge in the
  Web UI, and `heldBy: "cron"` in the API.
- `runwisp run <name>` still runs a held job by hand, so you can try it under
  RunWisp first.
- `runwisp takeover` ends the hold. If you retire cron some other way,
  stop it and disable it at boot (for example
  `sudo systemctl disable --now cron`). RunWisp notices within a minute and
  starts running the jobs, no reload needed. A stopped cron that is still
  enabled keeps the jobs held, because it starts again on the next boot.

Jobs from `/etc/anacrontab` are held the same way while anacron runs.

You never set a hold yourself. RunWisp checks for a running cron daemon on
every load.

### If RunWisp keeps crashing

The take-over installs a failsafe. If RunWisp crashes 5 times in 5 minutes and
systemd stops restarting it, the failsafe unmasks and starts cron, so your
crontab jobs keep running. Services and jobs that only `runwisp.toml` defines
stay stopped. Starting cron also runs its `@reboot` lines again. Restarts you
ask for with `runwisp restart` or `runwisp service install` don't count toward
the limit.

Once RunWisp is fixed, hand the jobs back to it:

```bash
sudo systemctl reset-failed runwisp.service && runwisp takeover
```

### Undoing it

```bash
runwisp service uninstall
```

Run as yourself, it re-runs itself with sudo. This unmasks cron (and anacron)
and restarts what was running, but only if this RunWisp's unit recorded the
take-over (a `# runwisp-masked-cron:` line in the unit). Once RunWisp is
stopped, cron comes back even if a later step fails. If something starts
cron again later, `runwisp service status` reports it and RunWisp holds the
jobs again within a minute. `runwisp takeover` fixes the cron side.

`runwisp service install` alone never retires cron. If cron still runs
jobs, it tells you to use `takeover`.

## In a container

A container has no systemd, so `takeover` stops there. Set RunWisp up in the
image instead, reading the crontab you already ship:

```dockerfile title="Dockerfile"
FROM php:8.4-cli
COPY --from=runwisp/runwisp:1 /usr/local/bin/runwisp /usr/local/bin/runwisp
COPY --chmod=0644 crontab /etc/cron.d/app
COPY runwisp.toml /etc/runwisp/runwisp.toml
ENV RUNWISP_HOST=0.0.0.0
CMD ["runwisp", "daemon"]
```

```toml title="runwisp.toml"
[daemon]
include_cron = ["/etc/cron.d/*"]
```

```bash
docker build -t myapp .
docker run -d --init -p 9477:9477 -e RUNWISP_PASSWORD=change-me myapp
```

- **Read or convert.** [`include_cron`](/configuration/daemon/#include_cron)
  reads the crontab as it is, so it stays the place you edit jobs. Like cron,
  it refuses a file others can write, hence `--chmod=0644`. To own the
  jobs as TOML instead, run `runwisp import cron crontab -o runwisp.toml` and
  copy that file in.
- **Drop cron from the CMD.** Remove `cron -f` or `crond` from the `CMD` or
  entrypoint; you no longer need the cron package. While cron runs next to
  RunWisp, the jobs are [held](#held-jobs) and RunWisp doesn't run them.
- **Listen on all interfaces.** The daemon listens on `127.0.0.1` by default,
  so without `RUNWISP_HOST=0.0.0.0` the dashboard is unreachable through `-p`.
- **Set a password.** Without `RUNWISP_PASSWORD`, the daemon makes up a new
  one on every start. Read it with `runwisp password` inside the container.

The rest of running RunWisp in your own image, such as services and `--init`,
is in [Running in Docker](/getting-started/docker/#inside-your-own-image).

## Convert by hand

`runwisp import cron` converts a crontab to TOML and prints it:

```bash
crontab -l | runwisp import cron        # your own crontab
runwisp import cron /etc/crontab        # a specific file
```

Given this crontab:

```text
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin
MAILTO=ops@example.com

# Nightly database backup
30 2 * * * /usr/local/bin/backup.sh --full
```

you get:

```toml title="runwisp.toml"
[tasks.nightly-database-backup]
description = "Nightly database backup"
cron = "30 2 * * *"
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
catch_up = 0  # cron never re-fires a missed tick
on_overlap = "queue"  # cron would overlap instead of queueing
run = "/usr/local/bin/backup.sh --full"

[tasks.nightly-database-backup.env]
PATH = "/usr/local/bin:/usr/bin"
```

The extra keys keep cron's behaviour; see
[How cron maps to RunWisp](#how-cron-maps-to-runwisp).

A summary goes to stderr, with one row per job:

| Mark | Meaning                                                  |
| ---- | -------------------------------------------------------- |
| `✓`  | Mapped cleanly.                                          |
| `~`  | Imported, but something changed. The row says what.      |
| `!`  | Needs a fix from you before the config loads.            |
| `-`  | Skipped, because your `runwisp.toml` already defines it. |

Notes about the whole file (such as `MAILTO`) are listed under `Notes:`.
Anything that can't be mapped gets a `# TODO` in the TOML. When it looks
right, save and check it:

```bash
crontab -l | runwisp import cron -o runwisp.toml
runwisp validate
```

If you already have a `runwisp.toml`, use `--write` instead of `-o`; see
[Staging and promoting](#staging-and-promoting). All flags are in the
[CLI reference](/reference/cli/#runwisp-import).

### System crontabs and the user column

`/etc/crontab` and files in `/etc/cron.d` have a user column between the
schedule and the command. The importer detects it from the path (or the
`# ... user command` header) and sets the task's
[`user`](/configuration/tasks/#user). For piped input, force it with
`--system` or `--system=false`.

A per-user crontab has no user column: cron runs it as the user it belongs to.
Import the spool file itself (`runwisp import cron
/var/spool/cron/crontabs/www-data`) and every task gets that `user`. A piped
`crontab -l` doesn't say whose it is, so its tasks run as the daemon's user
unless you add `user`.

### Retire the crontab

An import copies your jobs and never touches the crontab. If cron keeps running
them, every job runs twice. Before you start RunWisp, remove the imported jobs
from cron:

```bash
crontab -l > ~/crontab.backup    # keep a copy
crontab -e                       # comment out the imported lines
```

For a file in `/etc/cron.d`, move it out of the directory:

```bash
sudo mv /etc/cron.d/myjobs /root/myjobs.crontab.backup
```

:::danger[`crontab -r` can't be undone]
`crontab -r` deletes your whole crontab without asking. Take the backup first.
:::

You can move jobs one at a time. Never leave a job enabled in both cron
and RunWisp.

## Staging and promoting

`import --write` adds imported jobs next to a config you already have, without
editing your own tasks. It works the same for `import supervisord` and
`import systemd`.

```bash
crontab -l | runwisp import cron --write --dry-run   # show what would change
crontab -l | runwisp import cron --write             # do it
```

It uses two files:

```
runwisp.toml              # yours: hand-written, keep it in git
runwisp.d/imported.toml   # written by the importer
```

- Your `runwisp.toml` is created, or its
  [`include`](/configuration/daemon/#include) is set to load
  `runwisp.d/*.toml`. If you already have your own `include` list, `--write`
  doesn't change it; it prints the glob to add and writes nothing.
- The importer only ever writes `runwisp.d/imported.toml`, so you can run it
  again safely. Each run adds to what is staged. A job staged under the same
  name is replaced, and the summary lists what it kept and replaced.
- A job your config already defines with the **same** command is skipped (`-`).
  A job with the same name but a **different** command is renamed (`backup`
  becomes `backup-2`).
- Both files are written together. If anything fails, both are rolled back.
- If the result wouldn't load, nothing is written and the command exits
  non-zero, naming the jobs that don't load. Fix them and run it again, or use
  `-o` to get a file you can edit by hand.

Imported tasks show `"source": "staged"` in `runwisp list --json` and
`runwisp status --json`. They run like any other task.

### Promote a job

`promote` moves a job into your own `runwisp.toml`:

```bash
runwisp promote backup     # one job
runwisp promote --all      # every staged and crontab-read job
```

- **From staging**: the block moves from `runwisp.d/imported.toml` into your
  `runwisp.toml` as it is, comments and `# TODO` lines included. When the last
  job is promoted, the empty staging file is removed.
- **From a crontab** read by [`include_cron`](/configuration/daemon/#include_cron):
  the job is copied into `runwisp.toml`, and its line in the crontab is
  commented out with a note saying where it went. That stops cron from running
  it if cron is still active. If the line changed since the config was loaded,
  `promote` refuses and writes nothing; try again.

After promoting, the job is yours: it has no `source`, and a later import
doesn't touch it.

Run `runwisp reload` afterwards, or pass `--reload`. If the job was already
running under RunWisp (staged, or cron already retired), the reload reports no
task changes. If it was held because cron was still running, the reload reports
it as changed, and RunWisp starts scheduling it.

## How cron maps to RunWisp

These rules apply to `runwisp import cron` and to jobs read live through
[`include_cron`](/configuration/daemon/#include_cron).

| crontab                        | runwisp.toml                                                                             | Notes                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `30 2 * * * cmd`               | [`cron = "30 2 * * *"`](/configuration/tasks/#cron) + [`run`](/configuration/tasks/#run) | Copied as is.                                                                             |
| `@daily`, `@hourly`, `@weekly` | `cron = "@daily"` …                                                                      | Same names.                                                                               |
| `@midnight`, `@annually`       | `@daily`, `@yearly`                                                                      | Renamed to RunWisp's spelling.                                                            |
| `@reboot cmd`                  | [`run_on_start = "boot"`](/configuration/tasks/#run_on_start)                            | Once per machine boot.                                                                    |
| user column (system crontab)   | [`user`](/configuration/tasks/#user)                                                     | Detected automatically.                                                                   |
| `SHELL=/bin/bash`              | [`shell`](/configuration/tasks/#shell)                                                   | Must be an absolute path.                                                                 |
| `PATH=…`, `TZ=…`, other vars   | [`env`](/configuration/tasks/#env)                                                       | `TZ` is not a schedule zone in cron.                                                      |
| `CRON_TZ=…`                    | [`timezone`](/configuration/tasks/#timezone)                                             | Only `env` on Debian/Ubuntu. An unknown zone gets a `# TODO`.                             |
| `# comment` above a job        | [`description`](/configuration/tasks/#description)                                       |                                                                                           |
| `\%` in a command              | a literal `%`                                                                            |                                                                                           |
| `cmd % input`                  | `run = "cmd"` + a `# TODO`                                                               | See [below](#what-needs-a-human).                                                         |
| `MAILTO=…`                     | a `sendmail` notifier, printed for you to add                                            | See [below](#what-needs-a-human).                                                         |
| `cmd >/dev/null 2>&1`          | `run = "cmd"`                                                                            | Since 1.11, the redirect is dropped: cron needed it to stop mail, and RunWisp sends none. |

Crontab-wide settings (`SHELL`, `CRON_TZ`, variables) are copied onto each
task from that file. An import never changes your `[defaults]` or `[daemon]`.

### Environment and working directory

Every imported task gets [`env_base = "clean"`](/configuration/tasks/#env_base)
and [`working_dir = "~"`](/configuration/tasks/#working_dir), because your jobs
were written for cron:

- Cron gives a job an almost empty environment. Without `env_base = "clean"`,
  the job would get the daemon's environment. Your crontab's `PATH=` is still
  added on top.
- Cron's `PATH` is `/usr/bin:/bin`. A program elsewhere, like `php` in
  `/usr/local/bin` in the official PHP images, fails with exit 127 (command not
  found), under cron and RunWisp alike. The import notes each job this hits; add
  `PATH=` to the crontab.
- Cron runs a job in the user's home directory. Without `working_dir = "~"`,
  the job would run in the directory the daemon started in, and relative paths
  would point somewhere else. `~` is the home of the user the task runs as.

A job that starts with `cd DIR &&` gets `working_dir = "DIR"` instead, and the
`cd` is dropped from `run`. This applies when `DIR` is a plain absolute or
`~/` path.

### Catch-up and overlap

Both are written out, so you can delete the line to get RunWisp's behaviour:

- **[`catch_up = 0`](/configuration/tasks/#catch_up)**: cron never runs a job it missed while it was down.
  RunWisp normally [catches up](/configuration/tasks/#catch_up). The missed run
  is still recorded.
- **[`on_overlap = "queue"`](/configuration/tasks/#on_overlap)**: when a job is still running at its next time,
  cron starts a second copy. RunWisp waits for the first to finish instead. If
  your job must run in parallel, set
  [`max_concurrent`](/configuration/tasks/#max_concurrent).

For jobs read live through `include_cron`, you can't edit these lines;
`promote` the job first. RunWisp's cron syntax also accepts a seconds field and
`@every 30s`; see [`cron`](/configuration/tasks/#cron).

## What needs a human

- **`MAILTO`.** The summary prints a
  [`sendmail` notifier](/notifications/providers/sendmail/) for the address, to
  add to your `runwisp.toml`. It uses the same local mail setup cron used. Then
  add it to each task's [`notify`](/configuration/tasks/#notify). Cron mailed
  any output; RunWisp mails on failure. Without a local MTA, use
  [`smtp`](/notifications/providers/smtp/) instead.
- **`@reboot`.** [`run_on_start = "boot"`](/configuration/tasks/#run_on_start)
  runs once per boot, but only once the daemon is up. If the daemon starts
  late, or only after the boot, the job runs then. A command that never exits,
  such as a script that starts a server, belongs in a
  [service](/configuration/services/) instead.
- **A `%` that feeds input.** In cron, text after an unescaped `%` is sent to
  the job on stdin. RunWisp has no stdin setting, so the command is cut at the
  `%` and the input is quoted in a `# TODO`. Put it back into the command, for
  example with `printf '…' | cmd`.
- **A system crontab line without a user.** Cron skips it, and so does RunWisp.
  The sixth field must name a user that exists on this machine, so
  `* * * * * echo "tick"` is skipped (there is no user `echo`). Add the user and
  import again. A crontab from another machine is checked by its shape only.
- **Task names.** A short comment above the job names it, otherwise the
  command does (`/usr/local/bin/backup.sh` becomes `backup`). Jobs from a
  user's crontab or a `/etc/cron.d` file carry their source, so
  `/home/ops/bin/healthcheck.sh` in ops's crontab becomes `healthcheck-ops`.
  See [task names](/configuration/daemon/#include_cron) for the full rule.
  Rename any that aren't clear.

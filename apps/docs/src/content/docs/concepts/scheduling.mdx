The scheduler is meant to be predictable and unsurprising. It reads
standard cron expressions, fires the matching tasks at the right
moments, and records a row for every firing. There is no dependency
graph, no leader election — one daemon owns its tasks.

## The cron field

```toml
[tasks.heartbeat]
cron = "*/5 * * * *"
run  = "/usr/local/bin/heartbeat"
```

`cron` accepts standard 5-field syntax: **minute, hour, day-of-month,
month, day-of-week**. The usual convenience aliases also work:

| Expression              | Meaning                          |
| ----------------------- | -------------------------------- |
| `* * * * *`             | every minute                     |
| `*/5 * * * *`           | every 5 minutes                  |
| `0 * * * *`             | top of every hour                |
| `0 2 * * *`             | every day at 02:00               |
| `30 9 * * 1-5`          | weekdays at 09:30                |
| `0 0 1 * *`             | first of every month at midnight |
| `@hourly`               | top of every hour                |
| `@daily` / `@midnight`  | every day at 00:00               |
| `@weekly`               | Sundays at 00:00                 |
| `@monthly`              | 1st at 00:00                     |
| `@yearly` / `@annually` | January 1st at 00:00             |
| `@every 1h30m`          | every 90 minutes                 |

Six-field syntax (with seconds) is **not** supported. If you need
firings finer than a minute, use `@every 30s` or run a service.

## Timezone

Cron expressions are evaluated in the timezone configured by
`[scheduler] timezone`. **There is no implicit default** — if any task
has a `cron` expression, the daemon refuses to start without either
`[scheduler] timezone` or a per-task `timezone`. `0 2 * * *` silently
running at 02:00 UTC when the operator pictured local time is exactly
the kind of failure RunWisp won't allow.

```toml
# Daemon-wide default for every task without its own timezone.
# UTC is DST-free and a safe baseline; pick a local IANA zone if 2 AM
# should follow your wall clock.
[scheduler]
timezone = "Europe/Prague"

# Per-task override — any standard IANA timezone name works.
[tasks.nightly-backup]
cron     = "30 2 * * *"
timezone = "America/New_York"
```

| Setting                   | Default      | What it controls                                                                                              |
| ------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------- |
| `[scheduler] timezone`    | _(required)_ | Fallback for every task without its own `timezone`. Required when at least one cron task lacks a per-task TZ. |
| `[tasks.<name>] timezone` | _(inherits)_ | Timezone for this task's cron evaluation. Overrides the scheduler-wide default.                               |

Manual-only tasks (no `cron`) and `[services.*]` are unaffected — they
don't evaluate cron expressions, so a missing timezone never matters.

If the daemon doesn't recognise a name (typo, or missing timezone data
in a minimal Docker image), config load fails with the offending
scope — the daemon never silently falls back to UTC.

### DST behaviour

UTC has no DST. A daemon configured with `timezone = "UTC"` never
double-fires or skips around the clock change.

A daemon configured with a DST-affected timezone inherits the same
trade-off cron has had for 50 years: `0 2 * * *` fires **twice** on
the fall-back night (a real 02:00 happens twice) and **zero** times on
the spring-forward night (02:00 doesn't exist). If you need a fixed
local time without that hazard, either:

- keep the scheduler in UTC and write the cron in UTC, or
- use `@every 24h` (which respects elapsed time, not the system clock), or
- pick an hour outside the DST transition window (e.g. `0 4 * * *`).

Inside Docker, the Alpine base image strips timezone data by default;
add it back if you want non-UTC schedules:

```dockerfile
RUN apk add --no-cache tzdata
ENV TZ=Europe/Prague          # only affects the container's clock
```

The daemon's own `timezone` setting is what scheduling actually uses;
`TZ=` only affects log timestamps and shell commands inside `run`.

## What "fired" means

A cron tick triggers a **run**, not a side effect. Every firing produces:

- A row in SQLite with a fresh ULID.
- `triggered_by = "cron"`.
- A captured stdout/stderr stream on disk.
- A status of `pending → running → ended` with one of `success`,
  `failed`, `stopped`, `timeout`, `crashed`, `skipped`, or
  `log_overflow`.

Whether the run actually starts immediately depends on the task's
[concurrency policy](/concepts/concurrency/). With the default
`on_overlap = "queue"`, a tick that fires while a previous run is still
going gets queued. With `on_overlap = "skip"`, the firing is recorded
as a failed run with a "task already running" message and the schedule
moves on. Either way, the tick **always** appears in history — that's
the rule: nothing fails or fires without leaving a record.

## Missed ticks: catchup

When the daemon was down (host reboot, deploy, hard crash), some
scheduled firings didn't happen. The `catch_up` field controls what to
do about that on next startup:

```toml
[tasks.metrics-rollup]
cron     = "*/15 * * * *"
catch_up = "latest"      # default
```

| Policy   | Behaviour on startup                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| `latest` | If any ticks were missed, fire **one** catch-up run. Default. Right for jobs where running twice is harmless.     |
| `all`    | Fire **one run per missed tick**, capped by `max_catch_up_runs`. Right when each tick processes a discrete slice. |
| `skip`   | Pretend the missed ticks never happened. Right for monitors and probes that just want fresh.                      |

The anchor for "missed" is the timestamp of the last recorded run for
the task. On the very first boot, the anchor is the `first_seen_at`
recorded the moment RunWisp first parsed the task — so a fresh install
doesn't queue up a big batch of "catch-up" runs for ticks before the
daemon existed.

### Capping the backfill: `max_catch_up_runs`

`catch_up = "all"` on a `* * * * *` task and a daemon that was down for
a day means **1 440** runs queued at startup. The cap exists so a long
outage doesn't bury the scheduler.

```toml
[tasks.metrics-rollup]
cron              = "*/15 * * * *"
catch_up          = "all"
max_catch_up_runs = 200    # at most 200 missed ticks fire on startup
```

| Value     | Meaning                                                          |
| --------- | ---------------------------------------------------------------- |
| _omitted_ | Inherit the built-in default of **100**.                         |
| `0`       | Same as omitted — inherit the default.                           |
| `-1`      | Explicit unlimited. Every missed tick fires, no matter how many. |
| `N > 0`   | Cap the backfill at `N` runs; older missed ticks are dropped.    |

When the cap fires, the daemon logs a warning that names the task, the
total `missed`, the cap, and how many were dropped — so the silenced
ticks are never invisible (Prime Directive #1). The cap only applies
to `catch_up = "all"`. `latest` always triggers exactly one run by
construction, and `skip` triggers zero.

:::caution[`all` without a cap is a foot-gun]
If you set `max_catch_up_runs = -1` on a high-frequency task, accept
that a long outage backfills _every_ tick — possibly thousands — into
the queue at startup, governed by `on_overlap`. That's the right
answer for `pg_dump --since=...` where each slice is real work. It's
the wrong answer for `report.py` summarising "today" — switch that
one to `latest`, or pick a cap your queue can drain inside one cron
period.
:::

### Manual-only vs `catch_up = "skip"`

These two configurations look identical when you read the run history
("no backfill on startup"), but they're not the same thing — only one
of them is still scheduled.

| Configuration                        | When does it fire?                                  | Backfill on startup?             |
| ------------------------------------ | --------------------------------------------------- | -------------------------------- |
| **Manual-only** (no `cron` field)    | Only when triggered (`runwisp run-task`, REST, UI). | n/a — nothing to backfill        |
| `cron = "..."` + `catch_up = "skip"` | On every cron tick going forward.                   | None — missed ticks are dropped. |

If you don't want the task to run on a schedule at all, omit `cron`.
If you want it on a schedule but **never** want a startup backlog
("just resume the regular cadence"), set `catch_up = "skip"`. They
are different controls — manual-only removes the schedule itself,
`skip` keeps the schedule but discards the past.

## On startup: unfinished runs are marked crashed

On a clean shutdown the daemon waits for its running tasks to finish
or hit their timeout. On a hard crash (power loss, force kill), it
can't.

When the daemon next starts, **any run that was still recorded as
running is marked `crashed` with exit code `-2`**. Those runs are **not
resumed** — that would require knowing where the process got to, and
the daemon doesn't. A fresh run may then be created by the normal
scheduling / catchup logic above.

The point: every row in your run history finishes with a final
result. You never have a row stuck "running" because the daemon
disappeared under it.

## Predictable timing

Same TOML and same clock, same firings. There is no random delay —
two tasks with `cron = "0 2 * * *"` fire at exactly the same instant.
If that's a problem (they hit the same downstream service), stagger
the schedule explicitly:

```toml
[tasks.backup-a]
cron = "0 2 * * *"

[tasks.backup-b]
cron = "5 2 * * *"
```

## Reload semantics

The scheduler reads `runwisp.toml` once, at startup. There is no live
reload — no file watcher, no reload command. To pick up edits, restart
the daemon.

A parse error at startup fails the boot — the daemon exits before
opening its port. The safe pattern is to run `runwisp validate`
against the new file before you restart.

When a task disappears from the file across a restart, its schedule
entry is gone but its run history stays. When a new task appears, its
schedule is added; catchup does **not** apply for tasks that didn't exist
in the previous configuration.

## Intentional scope

A few things the scheduler doesn't try to do, on purpose:

- **No DAGs / task dependencies.** If `B` depends on `A`, chain them
  in one shell (`a && b`) or have `A` trigger `B` over the REST API.
- **No clustering.** One daemon owns its tasks. Two daemons reading
  the same TOML would both fire — that's a setup mistake, not a
  feature.
- **No "every Nth tick" semantics.** Cron is the surface; if you need
  every other Tuesday, encode it in the cron (`30 9 */2 * 2`) or
  filter in your script.

RunWisp is a cron replacement for a single operator, not a workflow
orchestrator.

Cron runs your jobs, but it doesn't _tell you anything_. A job fails at 3am and
the first you hear of it is a missing file the next morning. RunWisp keeps the
exact same schedules and turns every one of them into something you can watch:
per-run history, captured stdout/stderr, exit codes, and a notification when
something breaks.

You don't have to hand-translate your crontab. There are two ways in, and you
can start with either:

- **Point RunWisp at your crontabs and leave them there.** One line of config,
  no conversion, nothing rewritten. Best if you want visibility today and will
  tidy up later. Jump to [Read your crontabs as-is](#read-your-crontabs-as-is).
- **Convert to TOML with `runwisp import cron`.** You end up with a config you
  own, annotated with anything that needed a human's attention. Best if you want
  the crontab gone. That's the rest of this page.

## Read your crontabs as-is

If you'd rather not convert anything yet, hand RunWisp the files cron already
reads:

```toml
# runwisp.toml
[daemon]
include_cron = ["/etc/crontab", "/etc/cron.d/*"]
```

Start the daemon and every job in those files is a RunWisp task — captured
output, run history, notifications, a page in the UI — while the crontabs stay
exactly as they are. Edit one with `crontab -e`, run
[`runwisp reload`](/operations/reload/), and the change is live. When a job is
worth owning properly, `runwisp promote <task>` copies its definition into your
`runwisp.toml` and you delete the cron line whenever you feel like it.

Two things to know before you do this:

- **Disable cron first**, or every job fires twice — once from each scheduler.
  RunWisp warns at boot if it sees a cron daemon running, but it won't stop it
  for you.
- **A job RunWisp can't reproduce is skipped, not guessed at**, and the skip is
  reported by `file:line` at boot and by `runwisp validate`. The rest of the file
  keeps running. Run `runwisp import cron` on that file to see the full
  explanation for each one.

The full rules — which paths parse as the system format, what identity a job
runs as, how name collisions are resolved — are in
[`include_cron`](/configuration/daemon/#include_cron).

## The one-liner

Pipe your current crontab in, or point it at a file — both work the same way:

```bash
crontab -l | runwisp import cron        # whatever's installed for you
runwisp import cron /etc/crontab        # a specific file
```

That prints an annotated `runwisp.toml` to your terminal and a summary of what
it did. Given a crontab like:

```cron
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin
MAILTO=ops@example.com

# Nightly database backup
30 2 * * * /usr/local/bin/backup.sh --full
@reboot /opt/app/warmup
*/5 * * * * /opt/healthcheck.sh
```

you get:

```toml
[tasks.backup]
description = "Nightly database backup"
cron = "30 2 * * *"
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
run = "/usr/local/bin/backup.sh --full"

[tasks.backup.env]
PATH = "/usr/local/bin:/usr/bin"

# @reboot — runs once each time the daemon starts.
[tasks.warmup]
run_on_start = true
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
run = "/opt/app/warmup"

[tasks.warmup.env]
PATH = "/usr/local/bin:/usr/bin"

[tasks.healthcheck]
cron = "*/5 * * * *"
shell = "/bin/bash"
env_base = "clean"
working_dir = "~"
run = "/opt/healthcheck.sh"

[tasks.healthcheck.env]
PATH = "/usr/local/bin:/usr/bin"
```

Every task carries the crontab's `SHELL` and `PATH` itself, rather than a shared
`[defaults]` block — more verbose, but each task stands alone and your own global
settings are left untouched. The `env_base` and `working_dir` lines reproduce
cron's execution model rather than the daemon's — see
[How the pieces map](#how-the-pieces-map) below.

On stderr — so it stays out of the TOML you're piping somewhere — you get an
account of every job:

```
Imported crontab → 3 tasks
  ✓ backup        30 2 * * *
      /usr/local/bin/backup.sh --full
  ✓ warmup        @reboot
      /opt/app/warmup
  ✓ healthcheck   */5 * * * *
      /opt/healthcheck.sh

Notes:
  ! crontab sets MAILTO=ops@example.com. crond mails a job's output; RunWisp
    notifies on the event instead, so the closest equivalent is a sendmail
    notifier through the same MTA. Add to your root runwisp.toml:
        [[notifier]]
        id   = "mta"
        type = "sendmail"
        from = "runwisp@localhost"
        to   = ["ops@example.com"]
    then put notify_on_failure = ["mta"] on the tasks you want mail from. Note
    the difference: crond mailed any output at all, this mails failures.

Review the TOML above, save it as runwisp.toml, then run `runwisp validate`.

! cron still runs these jobs. Comment them out (`crontab -e`, or move the
  file out of /etc/cron.d) before starting RunWisp, or each one runs twice.
```

Every line of your crontab gets a row, and the row shows the command that will
actually run — wrapped if it's long, never cut short, because a `2>&1` you can't
see is a `2>&1` you can't check. The mark tells you how it landed:

| Mark | Means                                                    |
| ---- | -------------------------------------------------------- |
| `✓`  | Mapped cleanly.                                          |
| `~`  | Imported, but something changed — the row says what.     |
| `!`  | Needs a fix from you before this config will load.       |
| `-`  | Skipped, because your `runwisp.toml` already defines it. |

Anything about the file rather than about one job — a `MAILTO`, an unresolvable
`[include]` — lands in `Notes:` at the bottom. Nothing is dropped without a line.

When it looks right, save it:

```bash
crontab -l | runwisp import cron -o runwisp.toml
runwisp validate
```

`-o` writes the file (it won't clobber an existing `runwisp.toml` without
`--force`), and [`runwisp validate`](/configuration/overview/) confirms the
result parses before you start the daemon.

One thing left before `runwisp daemon`: importing **copied** your jobs, it
didn't take them away from cron. Turn cron off for them first — see
[nothing has retired cron yet](#nothing-has-retired-cron-yet) — and then the
same jobs run on the same schedules, except now they're all on the dashboard.

### Keeping your own config separate

`-o` gives you one flat file, which is perfect when you're starting fresh. If
you already have a `runwisp.toml` you've been hand-writing, use `--write`
instead:

```bash
crontab -l | runwisp import cron --write --dry-run   # look first
crontab -l | runwisp import cron --write             # then do it
```

`--dry-run` prints the same summary and names every file the real run would
touch, without touching any of them:

```
Would stage 3 tasks in /etc/runwisp/runwisp.d/imported.toml
Would create /etc/runwisp/runwisp.toml and wire it to load runwisp.d/*.toml.

Not checked: whether these merge with the tasks you already have.
A real run checks that, and rolls both files back if it fails.

! cron still runs these jobs. Comment them out (`crontab -e`, or move the
  file out of /etc/cron.d) before starting RunWisp, or each one runs twice.

Nothing was written.
```

The real thing installs the import in a **two-tier layout**:

```
runwisp.toml              # yours — hand-authored, keep it in git
runwisp.d/imported.toml   # machine-owned — the importer writes this
```

Your root file is created (or has its
[`[daemon].include`](/configuration/daemon/) wired) to load `runwisp.d/*.toml`,
and the imported jobs land in the staging file. Nothing you wrote by hand is
touched — the importer only ever owns `runwisp.d/imported.toml`, so you can
re-run the import without worrying about what it'll do to your own tasks. Both
files are written as one unit: if an imported job's name collides with a task
you already have, the whole write rolls back and tells you, rather than leaving
your daemon with a config it can't load.

Imported tasks report `"source": "staged"` in `runwisp list` and `status --json`
— shorthand for "came from an import, not native TOML yet". It's a label, not a
limitation: staged tasks are scheduled and run exactly like any other.

### Graduating a job into your own config

Staging is a waiting room. When you're happy with an imported job, promote it:

```bash
runwisp promote backup      # move this one into runwisp.toml
runwisp promote --all       # move all of them
```

That moves the job's block out of `runwisp.d/imported.toml` and into your own
`runwisp.toml`, comments and all — including any `# TODO` the import left for
you. Nothing is re-generated, so nothing gets reformatted or lost on the way.
From then on the job is yours: it reports no `source` any more, and a later
re-import won't touch it.

Nothing about the job's behaviour changes — only which file defines it. A
promoted service keeps running, and `runwisp reload` afterwards will honestly
report _no task changes_; the reload is just there to refresh the provenance
label on a live daemon. Use `--reload` to do both in one go, or `--dry-run`
first if you want to see exactly which bytes would move.

Convert one job a week or all of them at once — RunWisp doesn't mind. When the
last one is promoted the empty staging file is cleaned up, and you're left with
a single hand-maintained `runwisp.toml`, exactly as if you'd written it
yourself.

:::note
If your root config already sets its own `include` list, `--write` won't edit it
behind your back. It prints the glob to add and writes nothing.
:::

:::tip[System crontabs just work]
`/etc/crontab` and files in `/etc/cron.d` put a **user** between the schedule
and the command. RunWisp spots those automatically — from the path, or from the
`# m h dom mon dow user command` header — and maps that column to the task's
[`user`](/configuration/tasks/). You don't have to flag it.

If a piped crontab is ambiguous, the importer leaves a `# TODO` at the top of
the file rather than guessing wrong. Force the decision either way with
`--system` or `--system=false`:

```bash
runwisp import cron /etc/crontab -o runwisp.toml   # auto-detected
crontab -l | runwisp import cron --system=false    # never treat a column as a user
```

:::

## Nothing has retired cron yet

This is the one step nobody expects, so it gets its own heading: an import
**copies** your jobs into `runwisp.toml`. It doesn't touch your crontab, and it
can't — that's yours. Start the daemon with cron still enabled and every
imported job now has two schedulers firing it. Two backups. Two `find -delete`
sweeps. Nothing errors, so nothing tells you, which is exactly the kind of quiet
failure RunWisp exists to prevent — hence the `!` line at the bottom of every
import summary.

So before `runwisp daemon`, take the jobs away from cron:

```bash
crontab -l > ~/crontab.backup    # keep a copy, always
crontab -e                       # comment out the lines you imported
```

For a system crontab, move the file instead of editing it — cron picks up
`/etc/cron.d` by directory listing:

```bash
sudo mv /etc/cron.d/myjobs /root/myjobs.crontab.backup
```

Going all-in? `crontab -r` drops your user crontab entirely. Take the backup
first — it's unrecoverable, and it's the one command in this page you can't undo.

If you'd rather cut over gradually, that works too: comment out one job, let
RunWisp own it for a few days, then do the next. Just don't leave a job enabled
in both places — pick one owner per job and the schedules stay honest.

## How the pieces map

Most of a crontab translates one-to-one. Here's the whole picture:

| crontab                        | runwisp.toml                  | Notes                                            |
| ------------------------------ | ----------------------------- | ------------------------------------------------ |
| `30 2 * * * cmd`               | `cron = "30 2 * * *"` + `run` | The five fields are copied verbatim.             |
| `@daily`, `@hourly`, `@weekly` | `cron = "@daily"` …           | RunWisp speaks the same descriptors.             |
| `@reboot cmd`                  | `run_on_start = true` + `run` | Runs once each time the daemon starts.           |
| `@midnight`, `@annually`       | `@daily`, `@yearly`           | Normalized to RunWisp's spelling.                |
| user column (system crontab)   | `user = "..."`                | Detected automatically, `@reboot` lines too.     |
| `SHELL=/bin/bash`              | per-task `shell`              | Must be an absolute path.                        |
| `PATH=…`, other `VAR=val`      | per-task `env`                | Copied onto each task from that crontab.         |
| cron's minimal environment     | `env_base = "clean"`          | Set on every imported task — see below.          |
| jobs run in `$HOME`            | `working_dir = "~"`           | The home of whoever the job runs as.             |
| `CRON_TZ=…` / `TZ=…`           | per-task `timezone`           | Scoped to that crontab; a bad zone gets a TODO.  |
| `# a comment above a job`      | `description = "..."`         | The comment becomes the task's description.      |
| `\%` in a command              | a literal `%` in `run`        | Cron's escape, not the shell's — unwrapped.      |
| `cmd % input`                  | `run = "cmd"` + a `# TODO`    | Cron piped `input` on stdin; see below.          |
| `MAILTO=…`                     | a `sendmail` notifier         | Handed to you as a paste-able block — see below. |

Crontab-wide settings become **per-task** values rather than daemon-wide ones.
A crontab's `SHELL`, `CRON_TZ`/`TZ`, and top-of-file `VAR=val` lines are copied
onto each task the importer emits from that file, so importing a second crontab
with different values can't silently reach back and change the first one's
tasks — and nothing an import writes touches your global `[defaults]` or
`[scheduler]`.

Every imported task gets [`env_base = "clean"`](/configuration/tasks/#working-directory--shell).
Cron hands a job a nearly empty environment — `PATH=/usr/bin:/bin`, `SHELL`,
`HOME`, `LOGNAME` — so that's what your jobs were written against, and it's
what they keep. RunWisp's own default is to inherit the daemon's environment,
which is friendlier for a task you're writing today but wrong for one you're
moving: it would run with whatever the daemon was launched with, and you'd
find out weeks later. Your crontab's own `PATH=` line still lands in the
task's `env` and layers on top, so nothing you set explicitly is lost.

Cron also runs every job in the home directory of the user running it, while
RunWisp defaults to whatever directory the daemon was started in — so a `run`
script with a relative path in it would quietly write somewhere else. Every
imported job gets `working_dir = "~"`, and
[`~` means the home of whoever the task runs as](/configuration/tasks/#working-directory--shell):
the daemon's own account for a per-user crontab, and the user column's account
for a system crontab. Both formats end up with cron's rule, and neither needs
you to write a path.

RunWisp's cron grammar is a superset of vixie-cron's: the standard five fields,
descriptors like `@daily`, and a few extras (six-field specs with seconds,
`@every 30s`). [How scheduling works](/concepts/scheduling/) has the details.

## What needs a human

The importer never drops anything silently — anything it can't map cleanly
shows up as a `# TODO` in the file and a note in the summary. The usual ones:

- **`MAILTO`.** The summary hands you a
  [`sendmail` notifier](/notifications/providers/sendmail/) addressed to
  whoever the crontab named, ready to paste into your root `runwisp.toml`.
  It goes through the same local MTA cron used, so there's no relay host or
  password to find. It's a note rather than something the import writes,
  because a notifier is a daemon-wide setting and an import shouldn't reach
  into those.

    Two things to know. First, you still have to point the tasks you want mail
    from at it with [`notify_on_failure`](/notifications/per-task/) — the
    notifier alone sends nothing. Second, **cron mailed any output at all;
    RunWisp mails an event.** A job that printed a line and exited 0 used to
    generate mail and now doesn't. That's usually the improvement people wanted
    from cron mail, but it is a different rule — add `notify_on_success` if you
    really did want the chatty version.

    If the box has no MTA, or you'd rather point RunWisp straight at
    Gmail/SES/Postmark, [`type = "smtp"`](/notifications/providers/smtp/) is the
    same notifier with relay settings instead.

- **`@reboot`.** Mapped to [`run_on_start`](/configuration/tasks/), which fires
  once each time the **daemon** starts (not the machine). That's usually what
  you wanted; double-check if you were relying on true boot timing.
- **A `%` that fed a job input.** An unescaped `%` ends a crontab command;
  everything after it is what cron pipes to the job on stdin. RunWisp has no
  stdin field, so the command is imported cut at the `%` — exactly what cron
  ran — and the input it can't reproduce is quoted in a `# TODO` on the `run`
  line. Fold it back into the command yourself, usually with a here-doc or a
  `printf … | cmd`.
- **A system crontab line with no user column.** In `/etc/crontab` and
  `/etc/cron.d/*` the sixth field is the user to run as, and a line written
  without one is a mistake cron itself skips. RunWisp skips it too rather than
  guessing — reading the first word of the command as a username would give you a
  task that runs the wrong command as a user who doesn't exist. The line gets a
  `!` row quoting itself; add the user and re-import.
- **The task name.** Names are derived from the command (`/usr/local/bin/backup.sh`
  → `backup`). They're just labels — rename any that aren't obvious, and the
  full command is preserved either way.

## What you get that cron never gave you

- **History.** Every fire is a run with a start time, duration, exit code, and
  captured output — browsable in the Web UI and TUI, queryable over REST.
- **Failure that's loud.** A non-zero exit (or a missed tick while the daemon
  was down) can [notify you](/notifications/model/) instead of vanishing.
- **Overlap control.** A slow job that's still running when its next tick
  arrives no longer silently double-runs — pick
  [queue, skip, or terminate](/concepts/concurrency/).
- **Manual runs.** Trigger any job by hand from the dashboard or
  `runwisp exec <name>` without editing the schedule.

With the crontab lines gone, `runwisp.toml` is the one place your schedule
lives.

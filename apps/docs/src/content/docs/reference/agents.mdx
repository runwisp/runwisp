Everything an AI coding agent needs to work with RunWisp is in the binary or at
a stable URL.

## Point your agent at the docs

Add one line to your project's `AGENTS.md`, `CLAUDE.md`, or README:

```markdown
This project uses RunWisp. Machine-readable reference: https://docs.runwisp.com/llms.txt
```

- **[`llms.txt`](https://docs.runwisp.com/llms.txt)** is a compact index of the
  documentation for agents. `runwisp --help` prints the same pointer, and so
  does every subcommand's `--help` when its output isn't a terminal, which is
  how agents run commands.
- **[Agent reference](https://docs.runwisp.com/agents/reference.md)** is a dense
  summary of the whole `runwisp.toml` schema, the CLI, and the REST API. Start
  there.
- **Every page is also Markdown.** Append `.md` to a page URL, or send
  `Accept: text/markdown`.

## The config schema

```bash
runwisp schema
```

This prints the JSON Schema for `runwisp.toml`, also published at
[`https://docs.runwisp.com/config.schema.json`](https://docs.runwisp.com/config.schema.json).
To get validation and completion in editors, see
[Editor support](/configuration/overview/#editor-support-and-validation).

## Edit, validate, reload

To change tasks, an agent edits `runwisp.toml`, checks it, and tells the daemon
to reload:

```bash
runwisp validate --json   # non-zero exit on error; each error has key, line, column
runwisp reload            # apply it to the running daemon
runwisp run backup --json # run a task; the outcome is JSON on stdout, logs on stderr
```

`runwisp status --json` and `runwisp list --json` show the daemon's health, each
task's last run, and the configured tasks. The output shapes are in
[JSON output](/reference/cli/#json-output) and on each command in the
[CLI reference](/reference/cli/).

To see why a run failed, `runwisp logs backup -n 50` prints the last 50 lines of
the task's latest run and how it ended. It never waits for more output unless
you pass `-f`. See [`runwisp logs`](/reference/cli/#runwisp-logs).

An agent on the same machine as the daemon needs no password: the CLI talks to
it over the [control socket](/reference/cli/#control-socket). Neither the socket
nor the REST API can change a task definition; only `runwisp.toml` can.

## MCP server

**since**: `1.6`

`runwisp mcp` runs a [Model Context Protocol](https://modelcontextprotocol.io)
server on stdin and stdout, so an agent can call RunWisp without shelling out:

```bash
claude mcp add runwisp -- runwisp mcp
```

Every tool returns the same JSON its command prints with `--json`.

| Tool          | What it does                                                                       |
| ------------- | ---------------------------------------------------------------------------------- |
| `status`      | Daemon health and every task with its last run. Start here.                        |
| `runs`        | Run history, newest first, filtered by `task` or `status`.                         |
| `logs`        | Output of a task's latest run, or of a run ID. 100 lines by default, 1000 at most. |
| `search_logs` | Substring or regex search across a task's runs.                                    |
| `run_task`    | Trigger a task and wait for its outcome. Set `noWait` to return at once.           |
| `stop_run`    | Stop an active run.                                                                |
| `reload`      | Apply `runwisp.toml` to the daemon.                                                |
| `list`        | Tasks in the local `runwisp.toml`. Works without a daemon.                         |
| `validate`    | Check the local `runwisp.toml`. Works without a daemon.                            |

There is no tool that edits a task. The agent edits `runwisp.toml` itself, then
calls `validate` and `reload`.

For a daemon on another machine, either run the server there over SSH:

```bash
claude mcp add runwisp -- ssh host runwisp mcp
```

or pass `--url` (and `RUNWISP_PASSWORD`) to connect over HTTP. With `--url`,
`list` and `validate` are not offered, because they read a local file.
